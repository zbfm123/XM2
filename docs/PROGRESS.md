### ⚠️ 剩下一步：服务化（需要管理员权限）

当前 broker 是**独立进程**，重启机器后不会自动运行。注册 Windows 服务必须提权，所以这一步留给用户：

```powershell
# 以管理员身份运行 PowerShell，然后：
powershell -ExecutionPolicy Bypass -File D:\xmdeepseek\hospital-appointment\scripts\install-rabbitmq-service.ps1
```

脚本做的事：写系统级环境变量 → 停旧实例 → `rabbitmq-service install` →
**改成自动启动**（`sc config`，与 MySQL80 / Redis 一致）→ 启动 → 启用管理插件 → 验证并打印结果。
**幂等，可重复执行。**

> 脚本里最值得说明的一处设计：**用 `RABBITMQ_ERLANG_COOKIE` 固定 cookie 值**。
> 原因是踩了一个真实的坑（见下）。本地开发用已知值可以接受，
> 但**生产环境绝不该这样做**——正式环境应让 RabbitMQ 随机生成 cookie 并控制文件权限。脚本注释里写明了这一点。

### 踩坑：MQ 安装本身就有 4 个坑

| 坑 | 症状 | 根因与处理 |
| --- | --- | --- |
| **`RABBITMQ_LOGS` 指向目录** | broker 启动即崩，`Slogan: cannot_log_to_file, "d:/rabbitmq/data/log", eisdir` | 它要的是**日志文件路径**，不是目录。`erl_crash.dump` 里的 Slogan 是定位这类崩溃最快的入口 |
| **Erlang 在 Windows 不认 `HOME`** | `Failed to create cookie file 'd:/Users/tianliang/.erlang.cookie': enoent`——路径被拼坏 | 我一开始设 `HOMEDRIVE`+`HOME`，无效。用 `init:get_argument(home)` 探查才发现 **Erlang 读的是 `USERPROFILE`** |
| **服务与 CLI 的用户配置文件不同** | 服务以 LocalSystem 跑（cookie 在 `systemprofile`），你终端跑 CLI（cookie 在 `C:\Users\你`）→ **CLI 报连不上，而服务其实好好的** | 用 `RABBITMQ_ERLANG_COOKIE` 显式固定同一个值，两边都不再依赖配置文件路径。**这是"看起来像 MQ 坏了、其实是认证文件不匹配"的典型误判** |
| **`escript` 遇到 UTF-8 BOM 会挂** | `syntax error before ':'` | escript 要**无 BOM**；而 PowerShell 脚本**必须带 BOM**。同一台机器上两个相反的规矩，别搞混 |

> 还有一个顺手修掉的：Erlang 崩溃时把 `erl_crash.dump`（1MB+）写在**当前工作目录**，
> 污染了 `D:\xmdeepseek`。已设 `ERL_CRASH_DUMP` 指到固定位置。**项目 1 也踩过这个坑。**

### 2026-10-05：补上一个结构性覆盖缺口 —— MQ 打开时消费者没人测

**顺着"假绿"那条线往下查，发现了同源的第二个缺口。**

#### 缺口是什么

除了 `PaymentTimeoutIntegrationTest`，**所有集成测试都用 `test` profile，
而那个 profile 里 MQ 是关的**——也就是说挂号、取消这些业务测试
跑的都是 `NoopNotifier`。而 **dev 环境的默认是 MQ 打开**。

于是存在一个真实的空白：

> **"下单 → 经 RabbitMQ 投递 → 消费者写通知表" 这条链路，
> 在业务测试里从来没被走过。**

这与刚修掉的假绿问题**同源**：根因都是"**MQ 相关的验证只在很窄的一条路上做过**"。
假绿那次是消费者绑错队列导致消息没人消费，这次是干脆没有测试走那条路。

#### 修法：新增 `NotificationDeliveryIntegrationTest`（2 个用例）

| 用例 | 验证 |
| --- | --- |
| 挂号 → 经 MQ → 写出 `BOOKED` 通知 | 走完 **投递 → 消费 → 落库** 三段 |
| 取消 → 经 MQ → 写出 `CANCELLED` 通知 | 且先前的 `BOOKED` 仍在（两条独立记录）|

两个设计要点：

1. **轮询等待，不能下单后立刻断言。** 投递是异步的，下单接口返回时消息可能还在 broker 里。
   写成同步断言会随机失败，然后被人当成"flaky"忽略掉——
   **而这恰恰是"MQ 相关验证最容易被做假"的地方**。
2. **保留 `Assumptions` 探测 broker。** "干净机器 clone 下来 `mvn test` 就能全绿"
   是 N-04 的硬要求，不能被一个需要 broker 的测试破坏。
   探测不到就**跳过**（报告里显示 skipped，不是 pass）——
   **跳过是诚实的，假装通过才是危险的。**

#### 写这个测试时踩的坑（值得记）

第一版跑出来两个用例都失败：消费者日志明明打了"通知已记录"，测试却查不到。

原因：断言写成了 `type.equals(n.getType())`，而 `type` 是 `String`、
`n.getType()` 是 `NotificationType` **枚举**——
**`String.equals(枚举)` 永远返回 `false`**。测试白等 30 秒超时。

> **教训**：断言里类型不匹配时，**失败信息会把人引向错误的方向**——
> "没找到通知"看起来像投递或落库出了问题，实际只是比较方式写错了。
> 所以**断言失败时要先怀疑断言本身**，尤其在"日志显示成功但断言说没有"的时候。

#### 结果

测试数 **115 → 117**，全绿。现在 MQ 两侧的行为都有覆盖：

| 场景 | 覆盖它的测试 |
| --- | --- |
| broker **不可用**时挂号仍成功（A-07）| `MqUnavailableDoesNotBreakBookingTest`（4）|
| broker **可用**时通知真的落库（本次）| `NotificationDeliveryIntegrationTest`（2）|
| 延迟消息**真的**触发自动取消（A-06）| `PaymentTimeoutIntegrationTest`（5）|

### 2026-10-05：⚠️ 修掉一条**假绿**的测试 —— 测试里根本没有消费者

**这是本次最有价值的发现**，因为它意味着一条验收曾经是**假的**。

#### 怎么发现的

做 A-06 彩排时想缩短等待时间，用
`APP_APPOINTMENT_PAYMENT_TTL_MILLIS=15000` 启动应用，结果延迟队列的
`x-message-ttl` 仍然是 900000。顺着这条线查下去，发现两件事：

**问题一：延迟队列的 TTL 与业务时限是两套独立配置，且可以分家**

| 配置 | 作用 | 默认值 |
| --- | --- | --- |
| `app.appointment.payment-timeout-minutes` | 写进订单 `expire_at`（**业务时限**）| 15 分钟 |
| `app.mq.payment-ttl-millis` | 延迟**队列**的消息 TTL（决定消息何时投递）| 900000 ms |

队列 TTL 是**队列属性**，队列首次声明时就固定了——改配置**对已存在的队列无效**
（这个坑其实代码注释里写过，但只写了"需要重建队列"，没提两者会分家）。

更关键的是：`cancelOnTimeout` **完全没有校验 `expire_at`**，
收到消息就取消。所以队列 TTL 比业务时限短时，订单会被**提前取消**。
它自己的注释里明明写着"延迟消息只能表达'到了该检查的时间'……
到点之后该做什么，必须重新判断一次"——**而它没有重新判断时间**。

**问题二（更严重）：测试里的消费者压根没接上**

`@RabbitListener(queues = RabbitTopologyConfig.DEFAULT_NOTIFY_QUEUE)`——
用的是**硬编码常量** `appointment.notify.queue`，而测试配置里的队列名是
`appointment.notify.queue.test`。

后果：延迟消息死信转发进 `cancel.queue.test` 之后，**没有任何消费者**，
它会一直躺在那里。而那个"到期自动取消"的测试之所以显示通过，
是因为它等的是**别的东西**（服务层被别处调用过）。

> **它是一条假绿的测试。** 从测试结果里完全看不出来——
> 只有去 RabbitMQ 管理台，才会看到 `.test` 队列里堆着几十条没人消费的消息
> （实测 `cancel.queue.test` 66 条、`notify.queue.test` 70 条）。
> 那些堆积正是"没有消费者"的**物证**，而我最初把它当成了纯粹的卫生问题。

#### 修法（四步）

| # | 改动 | 目的 |
| --- | --- | --- |
| 1 | 新增 `QueueNameConfig`，用 **SpEL** 让监听器读配置的队列名 | 测试能真正覆盖消费者 |
| 2 | `cancelOnTimeout` 增加 **`expire_at` 校验** | 业务规则自己说了算，队列 TTL 只当投递延迟 |
| 3 | 业务时限改为**秒级**（`double` 分钟 + `plusSeconds`）| 测试能把两个数字**精确对齐** |
| 4 | 测试配置两者都取 **2 秒**（`2/60` 分钟）| 不再分家 |

#### 修的过程中又踩了三个小坑（都值得记）

1. **给 `@ConfigurationProperties` 的 record 加 `@Component` 会被拒绝**：
   > MqProperties is annotated with `@ConstructorBinding` but it is defined as a regular bean

   改用 `@Bean("queueNames")` 暴露**稳定的 bean 名**（SpEL 按名字找 bean，
   而 `@ConfigurationPropertiesScan` 生成的名字是 `app.mq-com.demo...MqProperties` 这种全限定名）。

2. **SpEL 里返回 `Supplier<String>` 是错的**：`queues` 属性要的是 String，
   而 `#{...}` 求值出来是个 Supplier 对象。**能被 SpEL 求值 ≠ 求值结果对**——
   这种错误编译期完全看不出来。改成 record 的直白访问器即可。

3. **断言精度**：`Duration.getSeconds()` 会**截断**——1998ms 变成 1 秒，
   报出来是"差 1 秒"，看着像业务 bug，其实只是断言方式选错了。
   另外 `created_at` 是**数据库**写入的时间戳，与 JVM 的 `now()` 有约 7ms 差，
   所以最终用了 2 秒容差（真 bug 是 898 秒的差，一抓一个准）。

#### 结果

| 项 | 修前 | 修后 |
| --- | --- | --- |
| 自动取消测试是否真的覆盖消费者 | ❌ **假绿** | ✅ 消费者真的接上了（`cancel.queue.test` 有消费者、消息被消费）|
| `.test` 队列消息堆积 | 66 + 70 条永久堆积 | **0 条** |
| 业务时限与队列 TTL | 分家（15 分钟 vs 1 秒）| **对齐（都是 2 秒）**，并有测试守这个不变量 |
| 测试数 | 114 | **115** |

> **最大的教训**：
> **"测试通过"和"测到了东西"是两件事。**
> 一条绿色的测试，如果它的依赖（消费者、队列、外部服务）根本没接上，
> 它就是一条**会骗人的测试**——而且比没有测试更危险，
> 因为它会让人放心地不去检查。
>
> 这次的物证（`.test` 队列里堆积的几十条消息）其实一直在那里，
> 我最初把它当成了无关紧要的卫生问题。**"没人消费的消息"本身就是信号。**

### 2026-10-05：并发走完整 HTTP 挂号链路（A-03 的第三处证据）

### 2026-10-05：我自己引入又修掉的 bug —— 测试清理把延迟队列删了

**这是本次唯一一个"由我的修复动作引入"的 bug**，值得完整记下来。

#### 起因

跑全量验证时 `PaymentTimeoutIntegrationTest.appointmentIsAutoCancelledAfterTimeout`
失败了（等了 60 秒超时），而它之前一直是 2 秒内通过的。

#### 排查过程（几个值得记的判断）

| 步骤 | 观察 | 结论 |
| --- | --- | --- |
| 1 | 单独跑该测试类 → **通过** | 不是代码坏了，是**测试之间互相影响** |
| 2 | 只跑那一个用例 → **通过**；整类一起跑 → **稳定失败** | 与执行顺序有关 |
| 3 | 加 DEBUG 日志看消息流转 | 单跑时"投递 → 1 秒后死信转发 → 消费者取消"三段全都正常 |
| 4 | 注意到失败的是**最后执行**的用例，而前面每个用例的 `@AfterEach` 都删了队列 | 嫌疑指向**我自己加的队列清理** |
| 5 | 临时去掉队列清理 → **整类通过** | 确认是它 |

#### 根因

我为了修"测试队列消息无限堆积"（实测堆了 66 + 70 条），在 `@AfterEach` 里写了
`rabbitAdmin.deleteQueue(...)`。但：

> **删掉队列后由 Spring AMQP 重新声明，而"删除 → 重新声明"之间有一个窗口。
> 此时投递的消息在 exchange 上找不到任何绑定，会被<静默丢弃>。**

最后执行的那个用例正好落在这个窗口里 —— 消息没进延迟队列，自然永远不会自动取消。

#### 修法

改用 **`purgeQueue`（清空消息，保留队列）**，而不是 `deleteQueue`。

连续跑 3 次整类，全部通过（26 秒左右）；全量 117 个测试稳定全绿。

> **教训（值得记住）**：
> **"清理干净"和"把东西删掉"不是一回事。**
> 对"声明与绑定由框架管理"的中间件（队列、交换机、Topic），
> **清空内容比删除实体安全得多**——删除会把框架管理的绑定关系一起弄没。
>
> 另外两条关于调试的经验：
> 1. **"只在整类运行时失败"是一个强信号**——它几乎总是指向测试间干扰
>    （共享状态、清理时机、执行顺序），而不是被测代码有问题；
> 2. 我一开始把这次失败当成"偶发"，差点就这么放过去了。
>    加上诊断输出后**立刻变成稳定复现**——**把不确定性变成确定性，
>    是修 bug 的第一步**。

### 2026-10-05：方法不支持的 405、以及容器层错误的格式统一

**发现方式：边界值探测。**（这类问题单测发现不了——单测都打正常路径。）

#### 问题一：方法用错返回 500，应为 405

用 `GET` 打 `POST /api/auth/login`，拿到的是 **500 "服务器内部错误"**。

根因：Spring 抛 `HttpRequestMethodNotSupportedException`，而这个异常没有专门的
处理器，掉进了 `@ExceptionHandler(Exception.class)` 兜底。

> ⚠️ **这已经是同一类问题的第三次出现**：
>
> | # | 场景 | 曾返回 | 应为 |
> | --- | --- | --- | --- |
> | 1 | 缺必填参数 | 500 | 400 |
> | 2 | 路径不存在 | 500 | 404 |
> | 3 | 方法不支持（本次） | 500 | 405 |
>
> 三次都是"少写一个 `@ExceptionHandler`，异常掉进兜底"。
> **兜底处理器保证不会漏出堆栈，但它会把一切归因成"服务端崩了"** ——
> 而这三件事都是**调用方的问题**，报 500 会让排查方向完全错位
> （用户去查服务端日志，真正的原因在他的 URL/参数/方法上）。
>
> 这也说明：**兜底分支是一把双刃剑**。它让系统"看起来不会崩"，
> 代价是掩盖了本该被区分的四类错误。

#### 问题二：容器层错误用了 Spring 默认格式

`POST /api/appointments//cancel`（空路径变量）返回的是：

```json
{"timestamp":"...","status":400,"error":"Bad Request","path":"..."}
```

而其它所有错误都是 `{code, message, path, time}`。

根因：这类请求**匹配不上任何 handler**，Spring Boot 把它转发到 `/error`，
由默认的 `BasicErrorController` 处理——**它绕过了 `GlobalExceptionHandler`**。

**两个后果**：
1. 同一个 API 出现**两种错误格式**，而"前端只需要一套解析逻辑"
   正是 `GlobalExceptionHandler` 明确追求的目标；
2. 默认控制器**会把原始异常消息放进响应体**，而本项目刻意对 5xx 返回泛化文案
   （异常细节可能含表名、SQL 片段、文件路径）——**默认控制器不受这条纪律约束**。

**修法**：新增 `UnifiedErrorController` 接管 `/error`，
把状态码翻译成同一套 `{code, message, path, time}`，且 5xx 不带原始消息。

| 请求 | 状态码 | 格式 |
| --- | --- | --- |
| `GET /api/auth/login`（应为 POST） | **405** | 统一 ✅ |
| `DELETE /api/departments`（应为 GET） | **405** | 统一 ✅ |
| `POST /api/appointments//cancel`（空变量） | 400 | 统一 ✅ |
| 不存在的路径（无令牌） | 401 | 统一 ✅ |
| 不存在的 api（有令牌） | 404 | 统一 ✅ |
| 缺必填参数 | 400 | 统一 ✅ |
| `page=0` | 400 | 统一 ✅ |

新增两条回归测试（`AuthIntegrationTest`，共 25 个用例）。

> 于是变成 404 而不是真实 Tomcat 上的 400。
> 所以断言写成"**是 4xx 且格式统一**"，而不是绑死某个状态码——
> 那条测试要守的是**格式**，不是某个具体数字。

### 2026-10-05：取消的并发竞态（用户取消 vs 超时自动取消）

**在防什么**：两条取消路径最终都会做
`transitionStatus(PENDING_PAYMENT → CANCELLED)` 然后归还号源。
如果两条都"成功地"归还，号源就被**归还两次**——
而号源多出来比少掉更危险：它意味着数据库里的数字不再可信，
而"不超卖"这个保证整个建立在"`remaining_slots` 恰好等于剩余量"之上。

**两层防线**（本测试同时验证）：

| 层 | 机制 | 保证 |
| --- | --- | --- |
| ① | 状态迁移是**带起始状态条件**的原子 UPDATE | 只有一个请求能把状态改走，另一个受影响行数为 0 → **不会去归还号源** |
| ② | 归还语句自带 `remaining < total` 上界 | 即使第一层被绕过，也**不可能把号源加超** |

#### 写这条测试时发现的一个测试有效性问题（值得记）

第一版只断言"号源恰好回到 10"。但 **因为有第二层上界兜底，
号源最多就是 10**——所以"恰好 10"**无法区分**
"只归还一次"和"归还了两次但被上界截断"。

**修法**：改为**数"谁真的执行了状态迁移"**——
HTTP 取消看响应里的 `replayed` 字段（`false` 才说明状态是我改的），
超时取消看 `cancelOnTimeout` 的返回值。断言**恰好 1 个**。

> 这一条比看号源数字精确得多：它证明的是**第一层防线生效**，
> 而不是"靠第二层侥幸没超"。

#### 反向验证

把 `transitionStatus` 的 `WHERE ... AND status = #{fromStatus}` 去掉（模拟"先查再改"）：

```
expected: 1
 but was: 6
```

**6 个并发取消全部"成功"了**——测试立刻失败，证明这条断言确实在守第一层防线。
验证后已 `git checkout` 完整恢复（`git diff HEAD` 无差异），全量测试重新全绿。

### 2026-10-05：幂等的**并发**边界（号源泄漏的防线）

**为什么单独测**：已有的幂等测试覆盖的是**串行**重复提交——
第一次成功，之后同键命中"幂等快路径"。
但真实的重试往往是**并发**的：用户双击、或前端超时后重发，
两个请求几乎同时到达，**都会走到"快路径查不到"这一分支**，
然后一起去扣号源、一起插入订单。

代码里为此专门写了兜底（`catch (DuplicateKeyException)` 后**归还号源**、
返回先到者的订单）。**但这条路径只用单线程测过——等于没测**，
而并发代码最典型的错误就是"单线程跑得好好的"。

#### 两条用例，最后一条断言最关键

| 用例 | 断言 |
| --- | --- |
| 同一幂等键并发到达 8 次 | 只建 **1** 单、8 个响应**同一个单号**、**号源只扣 1 个**、无一 500 |
| 不同幂等键但同一排班并发到达 | 只建 **1** 单（活跃订单唯一索引守住）、**号源只扣 1 个** |

第三条断言是重点：**失败的那些请求必须把多扣的号源还回去**。
漏了归还，号源就会凭空少一个——表现为**系统性地丢号，而且不会有任何报错**。

#### 反向验证：证明这条测试真能抓到号源泄漏

把 `catch` 分支里的归还那行去掉（`int returned = 1;`），重跑：

```
expected: 9
 but was: 2
```

8 个并发请求把号源从 10 扣到了 **2**（泄漏 7 个）。测试立刻失败，**证明它有效**。
验证后已用 `git checkout` 完整恢复，并确认与 HEAD 无差异、测试重新全绿。

### 2026-10-05：验证令牌失效的三种分类（前后端协作点）

**为什么验证这个**：前端 axios 拦截器对**任何 401** 都会清登录态并跳登录页——
这个行为一直没在真实链路上验过。更值得验的是**后端有没有区分**不同失效原因，
因为那是"能不能给用户正确提示"的前提（"登录已过期" vs "令牌无效"是两件事）。

**方法**：用同一个 secret 自己签三种令牌（`/api/auth/me` 逐一代入）：

| 令牌 | 后端返回 | 判断 |
| --- | --- | --- |
| 同一 secret，但 `exp` 在过去 | `TOKEN_EXPIRED` | ✅ |
| 别人的 secret 签名 | `TOKEN_INVALID` | ✅ |
| `iss` 不是 `hospital-appointment` | `TOKEN_INVALID` | ✅ |

**结论**：后端的分类是按 **JWT 标准声明**做的，不是"猜"的——
过期由 `exp` 判定、签名与 issuer 由解析器校验，两者走的是不同的异常分支
（`ExpiredJwtException` vs `JwtException`），所以能准确区分。

**顺带确认了令牌载荷是干净的**：

```json
{"sub":"1","iss":"hospital-appointment","jti":"...","iat":...,"exp":...}
```

只有标准声明 + `jti`，**没有任何用户信息**（没有手机号、姓名、角色）。
这与 `JwtService` 的注释一致：需要用户信息时回库读，
这样"账号被停用"能立刻生效，而不是等令牌自然过期。

**前端的处理是对的**：它对**所有** 401 一视同仁地跳登录页，不去分支判断
`TOKEN_EXPIRED` 与 `TOKEN_INVALID`——因为对用户而言两者的动作完全相同
（重新登录）。**过度区分反而会让前端多出两条没有实际差别代码路径。**

### 2026-10-05：Redis 从"必需"降级为"可选"（由诚实性核对引出）

**起因**：修 Redis 文档不一致时想到一个反问——
既然代码一处都没用到 Redis，那"Redis 必须在跑"这个要求成立吗？

**实测**（两次，第二次才是真的排除）：

| 尝试 | 结果 |
| --- | --- |

| 强杀 `redis-server` 进程 | ❌ 被 Windows 服务自动拉起（6379 又回来了）|

### 2026-10-05：补上模拟支付回调 —— 让 PAID 与 COMPLETED 在接口层可达

**这是一个真实的功能缺口，不是锦上添花。** 它是核对文档时发现的：

- 任务书（04）里**没有**支付任务
- 但 `docs/02` 的 D-07 写着"挂号的支付用**模拟回调**，不接真实支付"
- 而实现里**没有任何入口**能把订单推进到 `PAID`

后果有两个，第二个更严重：

| 后果 | 说明 |
| --- | --- |
| 状态机有两条路径亮不起来 | `PAID` / `COMPLETED` 只能靠测试手动改库到达 |
| **"已支付的订单不会被超时误取消"演示不出来** | 演示"15 分钟未支付自动取消"只讲了一半；另一半（已支付的不该被取消）**没有入口去制造那个场景** |

> 第二条是关键：`AppointmentStatusMachineTest` 证明了状态机**枚举内部自洽**，
> 但证明不了**"订单真的能沿着状态机走完"**。规则对，不代表规则被用上。

#### 实现

| 端点 | 迁移 | 说明 |
| --- | --- | --- |
| `POST /api/appointments/{no}/pay` | `PENDING_PAYMENT → PAID` | 模拟支付回调（D-07）|
| `POST /api/appointments/{no}/complete` | `PAID → COMPLETED` | 就诊完成（真实系统里由 HIS 回调或定时任务推进）|

底层是**一个**通用方法 `advanceStatus(userId, no, target, note)`，而不是两个：

> 两个动作的**执行结构完全相同**——带起始状态的原子 UPDATE、
> 受影响行数为 0 说明状态已被别人改过、只做通知不做补偿。
> 写成两份会复制这个结构，将来改一处忘一处。

**⚠️ 合法性的唯一判据是状态机的 `canTransitionTo`**，所以它天然做到了：
不能跳步（`PENDING_PAYMENT` 不能直接到 `COMPLETED`）、**终态不可被回调复活**、不可自环。
**没有在 Controller 里重新实现一遍规则**——那是最容易和状态机长歪的地方。

**⚠️ 关于安全性，代码注释里写明了**：真实系统里这个入口必须校验支付平台签名与金额，
否则任何人构造一个请求就能把订单标记成已支付。本项目支付是主动砍掉的
（`docs/01` 的不做清单），端点只在本地演示环境存在，命名上直接叫 `pay`（模拟）。

#### 测试（`AppointmentLifecycleIntegrationTest`，8 个）

| 用例 | 断言 |
| --- | --- |
| 全生命周期 | `PENDING_PAYMENT → PAID → COMPLETED` **在接口层真的可达** |
| 已支付不可取消 | 409 `INVALID_STATE`（退号涉及退费，本项目不做真实退费）|
| 终态不可复活 | `COMPLETED` 既不能支付也不能取消 |
| 不能跳步 | 未支付直接标完成 → 409 |
| **重复支付回调幂等** | 第二次返回 `replayed=true`（真实回调会被平台重投）|
| 越权 | 用别人的单号支付 → 404 |
| 需登录 | 两个端点未登录均 401 |
| 支付不归还号源 | 已支付的单仍正常占用一个号 |

#### 顺带扩了端到端验收

`scripts/verify-e2e.ps1` 的 A-10 闭环从 18 项扩到 **22 项**，
补上支付、已支付不可取消、就诊完成、终态不可再取消——
现在它覆盖**状态机的全部四条路径**。

> 扩展时第一版失败了 1 项，而且**是我的断言写错了**：
> 支付/完成那一单会一直占用号源（这是正确行为），
> 但我把"号源归还"的断言放在它之后，读到的是它的占用。
> 修法是给支付流程用**另一条排班**，让两组断言互不干扰。
> 这类"测试自身造出的干扰"很容易被误判成代码 bug——记录在此提醒。

### 2026-10-05：修掉一个真实的复现性缺口 —— 库要手工建

**发现过程**：核对 A-09「新机器可复现」时，去查 README 的启动步骤，
发现它要求先手工执行 `CREATE DATABASE`。

**实测验证（真实地把库删掉）**：

| 步骤 | 结果 |
| --- | --- |
| `DROP DATABASE hospital_appointment` | 库确认不存在 |

#### 两个配置细节，都属于"写错不会报错、只会行为不对"

**① `proxy_pass` 结尾不能有多余的 `/`。**
写成 `proxy_pass http://127.0.0.1:8081/;` 会**剥掉 `/api` 前缀**，
后端收到 `/auth/login` 而不是 `/api/auth/login`，全部接口 404。
这次验证里"登录经代理"那一项专门守的就是它。

**② `include mime.types` 的路径相对"配置文件所在目录"，不是 nginx prefix。**
我一开始把站点配置放在 `conf/sites/` 下，于是 nginx 去找 `conf/sites/mime.types`，
报 `CreateFile() ... failed`。解法是把 `mime.types` 一起放进 `deploy/nginx/`，
让配置自包含——顺带也不再依赖"nginx 装在哪个目录"。

#### 顺带抓到一个真 bug：请求不存在的路径返回 500

验证第 ⑥ 项（"未匹配的 /api 是否被正确转发给后端"）时，后端回了 **500 "服务器内部错误"**。

- **根因**：`GlobalExceptionHandler` 没有处理 Spring 6.1 的 `NoResourceFoundException`，
  异常掉进兜底分支变成 500
- **为什么是问题**：**路径打错了是调用方的问题，不是服务端崩了**。
  用户看到 500 会去查服务端日志，而真正的原因是他的 URL 拼错了
- **修法**：加 `@ExceptionHandler(NoResourceFoundException.class)` → 404 + `NOT_FOUND`
- **防回归**：`AuthIntegrationTest.unknownPathShouldReturn404NotServerError()`

> 这是第二次出现同一类问题（第一次是"缺少必填参数返回 500"）：
> **少写一个 `@ExceptionHandler` 不会编译报错，只会静默返回错的状态码。**
> 而两次都是被"真实链路的手工验证"发现的，不是被单元测试发现的——
> 因为没人会想到去测一个"我根本没写的接口"。

### 2026-10-05：T-010 RabbitMQ / T-011 MQ 不可用不影响挂号 / T-012 超时自动取消

- **验收 A-06（延迟队列自动取消）与 A-07（MQ 挂了挂号仍成功）已通过**
- 测试：**89 → 97 个，全绿**；其中 4 条在**真实 RabbitMQ** 上跑

#### 拓扑

```
挂号/取消 ──→ appointment.exchange (topic) ──→ appointment.notify.queue ──→ 消费者写 notification 表

下单 ──→ appointment.delay.exchange ──→ appointment.delay.queue
                                          (TTL 15min，**故意没有消费者**)
                                               │ TTL 到期成为死信
                                               ▼
                                        appointment.dlx ──→ appointment.cancel.queue
                                                                  ──→ 消费者检查状态 → 取消 + 归还号源
```

用 **TTL + 死信交换机**而不是延迟插件（决策 D-05）：插件要额外安装，而 DLX 是标准机制、面试更常问。
关键点：**延迟队列自己不消费**——没有消费者，消息只能等到过期。

#### 三个刻意的设计决定

**① 整套 MQ 组件挂在 `app.mq.enabled` 下，默认关闭。**
否则在没装 broker 的机器上，应用启动时就会去连 broker、连不上就抛异常，
**连"启动"这一步都过不去**——那样 A-07 就成了空话。
默认关闭同时保证了 `mvn test` 不依赖 broker（N-04"干净机器可复现"的一部分）。

**② MQ 关闭时用 `NoopNotifier` 显式实现"什么都不做"，而不是干脆不注册 Bean。**
不注册会让依赖 `Notifier` 的 `AppointmentService` 起不来，而"MQ 没开"恰恰是必须能正常工作的状态。
这也说明：**"不启用某功能"应当是一个显式的实现，而不是一段缺失的代码。**

**③ 消息用 JSON 序列化，不用 Java 原生序列化。**
Java 序列化的消息在管理台里是一串乱码，演示时点开给面试官看什么都看不到；
而"能在管理台看到消息内容"正是 MQ 最好讲的地方。

#### T-011 暴露出一个真实的设计缺口（已修）

`Notifier` 接口上写着"绝不抛异常"，但**约定靠人遵守，人会漏**；
框架代码（`RabbitTemplate`、连接池）抛的正是异常。
测试用了一个"总是抛异常"的桩，**挂号立刻被打挂**。

修法：调用方也加兜底（`tryNotifyBooked` / `tryScheduleTimeout`），
于是 A-07 从"取决于实现者记得 catch"变成**"无论实现怎么写都成立"**。
这是第二道防线，与号源的唯一索引、状态机的条件 UPDATE 是同一种思路。

#### T-012 最关键的判断：延迟消息只能表达"该检查了"，不能表达"该执行了"

延迟消息是**下单那一刻**发出的，15 分钟后才回来，而这 15 分钟里用户可能已经**付款**了。
如果消费者不看状态就取消：

```
13:00  下单，发一条 15 分钟延迟消息
13:05  用户支付成功 -> PAID
13:15  延迟消息到期 -> 把 PAID 改成 CANCELLED 并归还号源
```

结果是**用户付了钱、号被取消、号源还被卖给了别人**——同时伤害用户和医院的账。

因此取消动作必须是**带起始状态条件的原子 UPDATE**（与用户主动取消同一条路径）：
受影响行数为 0 说明"它已经不是我该取消的那个状态了"，此时**什么都不做**。

> 已写成测试（`paidAppointmentMustNotBeCancelledByTimeout`）：
> 下单 → 手工推进到 PAID → 等超过 TTL → 断言状态仍是 PAID 且号源未被归还。

#### 又一个"保护措施没接上"：`application-dev.yml` 的重复顶层键

在文件末尾追加 MQ 配置时写了**第二个顶层 `app:` 和第二个 `spring:`**，
启动时 snakeyaml 直接抛 `DuplicateKeyException`，
而它的报错只说 `while constructing a mapping`——**不告诉你是哪一行重复**。
已重写为单段，并在文件头写明"这个文件只允许有一个顶层 spring: 和 app:"。

（这也是同一主题的第 N 次出现：配置、索引、事务边界、BOM 守卫……
**每一次的代码都"看起来是对的"。**）

#### 测试策略：唯一需要真实 broker 的那一份怎么放

`PaymentTimeoutIntegrationTest` 是唯一需要真 RabbitMQ 的测试（TTL 到期后的死信转发是 **broker 行为**，
H2 + 桩测不出来）。做法：

- 独立 profile `application-mqtest.yml`：打开 MQ、**TTL 改成 1 秒**、队列名加 `_test` 后缀
  （TTL 是**队列属性**，一旦队列存在就没法改；独立队列名让测试可反复运行而不必手工删队列）
- 类内用 `Assumptions` 探测 broker，**不可达时跳过而不是失败**——
  没有 broker 的机器跑全量测试依然全绿
- 但跳过**必须有声音**：打印明确提示说明"A-06 这次没有被验证"。
  **静默跳过是最糟的**——它让人以为功能测过了

### 2026-10-05：T-007 提交挂号 / T-008 取消挂号 / T-009 我的挂号

- 端点：`POST /api/appointments`、`POST /api/appointments/{no}/cancel`、`GET /api/appointments`
- **验收 A-04（幂等）、A-05（归还号源）已通过**；15 个集成测试 + 真实 MySQL 冒烟

| 纪律 | 做法 |
| --- | --- |
| 幂等键**必填** | 不做成可选——否则"防重复提交"变成依赖客户端自觉的功能 |
| 幂等快路径 | 同键重复提交直接返回已有订单，**连号源都不碰** |
| 号源只在**真正改变状态**那一次归还 | 取消时用"带起始状态的原子 UPDATE"，受影响行数 0 即说明已被别人改过 |
| 越权防护 | **接口不接受 userId 参数**，一律从登录上下文取；用别人的单号取消返回 **404**（不泄露单号是否存在） |
| `replayed` 字段 | 用数据表达"这次是不是重放"，而不是靠状态码的细微差别 |

#### 又抓到两个真 bug（由 A-04/A-05 测试暴露）

**① 重复取消返回 409，而不是幂等成功。**
A-05 明确要求"重复取消幂等"。原实现先判"是否终态"、终态一律拒绝，
于是 `CANCELLED → CANCELLED` 被当成非法操作。
但用户的第二次点击（或前端重试）**目标已经达成**，返回 409 只会让前端多写一个无意义分支。
修法：`CANCELLED` 单独走幂等成功分支。

**② 取消后无法重新挂同一个号 —— 这是 T-002 就埋下的索引设计缺陷。**
原来的 `uk_appointment_user_schedule (user_id, schedule_id)` 把**已取消**的单也算进唯一性，
于是"取消 → 想重挂"被数据库拒绝，用户看到"您已挂过该排班"，而他的号早就取消了。

正确的业务语义是"同一排班**同时只能有一个活跃订单**"，
而不是"历史上只能挂过一次"。修法：改用**生成列**表达：

```sql
dedup_key BIGINT AS (IF(status = 'CANCELLED', NULL, user_id)) STORED,
UNIQUE KEY uk_appointment_active_slot (dedup_key, schedule_id)
```

活跃订单 `dedup_key = user_id`（参与唯一性），已取消为 `NULL`
（MySQL 的 UNIQUE 允许多个 NULL，天然不参与约束）。
**"防并发重复下单"这个真正需要数据库保证的能力一点没丢**，
同时把"取消后可以重挂"这个正常业务路径还给了用户。

> ⚠️ **同一个修正必须同时落在三处，这是本次最容易漏的地方**：
> `db/schema.sql`、`test/resources/db/schema-h2.sql`、**以及开发库里那条已经存在的索引**。
> 前两处不影响已运行的数据库——**开发库需要手工 ALTER**（已执行）。
> 这类"代码改了但线上/本地的既有结构没跟着改"的问题，
> 表现是"测试全绿、真实环境照旧出错"。

> **这条也再次印证了那句主题**：保护措施没接上。
> 唯一索引在前几个任务里被反复称赞为"第二道防线"，
> 但**它约束的语义如果不是业务真正想要的，它就会变成一道拦错人的防线**。

### 2026-10-05：T-006 号源扣减（防超卖）← 技术内核

- 交付：`ScheduleMapper.tryDeduct()` 与 `tryReturn()`，各是**一条**带条件的原子 SQL
  ```sql
  -- 扣减：判断与扣减在同一语句里，中间没有窗口
  UPDATE schedule SET remaining_slots = remaining_slots - 1
   WHERE id = ? AND remaining_slots > 0

  -- 归还：**带上界判断**，否则重复取消会把号源加超总数
  UPDATE schedule SET remaining_slots = remaining_slots + 1
   WHERE id = ? AND remaining_slots < total_slots
  ```
- 用**受影响行数**回答"抢到没有"（1 = 抢到，0 = 已满）；**失败不补偿**

#### 验收 A-03：两处独立证据（这是本项目的立身之本）

| 证据 | 环境 | 结果 |
| --- | --- | --- |
| `ScheduleConcurrencyTest`（5 个测试） | **H2**（MODE=MySQL） | 1000 线程抢 20 号 → 成功恰好 **20**、剩余恰好 **0**、无负数 ✅ |
| `scripts/verify-concurrency-on-mysql.ps1` | **真实 MySQL 8.0.40 / InnoDB** | 成功恰好 **20**、被拒 **980**、剩余 **0** ✅ |

**为什么要两处都跑**：本项目依赖的是 **InnoDB 的行锁**，而 H2 的锁实现与它不同。
H2 的绿灯只能证明"这条 SQL 语法对、逻辑对"，**不能证明"在 InnoDB 上原子"**。
只跑 H2 就宣称防超卖成立，是拿一个近似实现的行为替代真实实现的行为——
而这两者恰恰可能在锁上不同。

> 同时保留 H2 版本的理由：**任何人 `mvn test` 都能复现**（N-04"干净机器可复现"的一部分）。
> MySQL 那份被做成**独立程序 + 脚本**，而不是一个 `@SpringBootTest`，
> 正是为了不让"必须有 MySQL 才能跑"污染测试套件。

#### 两次反向验证：证明测试真的能抓到错

一条永远通过的测试，和一条真能抓错的测试，在 CI 里看起来一模一样（都是绿色）。
所以这两处都对着**已知的错误实现**跑过一次：

| 验证对象 | 植入的错误 | 结果 |
| --- | --- | --- |
| H2 的 `ScheduleConcurrencyTest` | 把原子 UPDATE 换成"先查再改" | **失败**：`expected: 20 but was: 64`（超卖 3 倍多）✅ |
| MySQL 的验证程序 | 同样的错误写法（作为对照组保留在程序里） | **超卖 63 个**（成功 83 / 剩余 -63）✅ |

**第二条尤其重要**：验证程序里**永久保留**了那个错误实现作为对照组。
它每次都跑一遍，并且**要求它必须查出超卖**——查不出来才算失败。
这样"验证程序本身有没有检测能力"就成了每次运行都会检查的事，
而不是靠某一次手工确认。

#### 归还号源的上界（T-008 的防线，在这里一并锁定）

`tryReturn` 若不带 `remaining_slots < total_slots`，重复取消就会让号源**超过总数**。
号源变多比变少更危险：它意味着数据库里的数字已经不再可信，
而"不超卖"这个保证整个建立在"`remaining_slots` 恰好等于剩余量"之上。

已测：扣 5 → 剩 15 → 归还 20 次**只有 5 次成功** → 恰好回到 20，不过界。

## 踩坑记录

### T-004：三个缺陷，全部由新写的测试当场抓出来

这一轮值得记的不是"写了什么功能"，而是**新测试第一次跑就红了 3 条**——
三条都是真问题，只是每一条的"性质"不同：

| # | 症状 | 性质 | 根因与修复 |
| --- | --- | --- | --- |
| 1 | `departmentName` 显示成了**医生名** | **静默的数据串位**（最危险的一类） | JOIN 里医生表和科室表**都有 `name` 列**，结果集出现两个同名标签，构造器映射选错了列——**而且不报错**。修复：每个列显式起别名，别名 = record 字段名，让映射变成按名字而不是按位置 |
| 2 | 缺 `deptId` 时返回 **500** | **状态码归错责任方** | 少一个 `@ExceptionHandler(MissingServletRequestParameterException.class)`，异常掉进兜底变成"服务器内部错误"。**调用方少传参数，却让前端去查服务端日志**。已补：400 + `INVALID_PARAMETER` |
| 3 | 分页响应里**没有 `totalPages`** | **序列化漏字段** | Jackson 只把 `getXxx()` 当属性，`record` 内自定义的 `totalPages()` 默认不序列化。前端拿不到总页数，分页器只能显示"上一页/下一页"。已补 `@JsonProperty("totalPages")` |

> **这三条都不是"功能没做完"，而是"功能看起来做完了但结果是错的"**——
> 和 T-003 那两个坑同一类。共同点：<b>编译器不会报错，只有断言会。</b>
> 结论仍然是那句：写完一个查询，要用测试去断言**取回来的每个字段到底是什么**，
> 而不是只断言"HTTP 200 且 list 非空"。

**第 1 条特别值得讲**（面试也是一个好例子）：
两个表有同名列 + 靠位置映射 = 一条不会报错的错误。
它的表现（"科室名那一栏是医生名"）和它的原因（SQL 列标签歧义）之间的距离非常远，
**如果没有断言具体字段值，它会一路活到演示现场**。

### 还有第 4 条：BOM 守卫"只守它记得的那个目录"

| 项 | 内容 |
| --- | --- |
| **症状** | `push.ps1` 里有一道"`.ps1` 必须有 UTF-8 BOM"的守卫，但它用 `-File -Filter *.ps1` **只扫项目根目录**。新加的 `scripts/install-rabbitmq-service.ps1` 完全不在保护范围内——守卫形同虚设，而且**它自己不会报错**。 |
| **根因** | 守卫写下的那天，仓库里只有根目录一个 `.ps1`。后来脚本进了子目录，守卫没有跟着覆盖到新位置。 |
| **修复** | 改 `-Recurse` 并排除 `target/node_modules/.git`；报错时输出相对路径而不是文件名。 |

> ⚠️ **这条和上面三条、以及 T-003 的两条，是同一个主题的第五次出现：**
> **"保护措施没有真正接上"**——事务边界没接上（锁定失效）、唯一索引没接上（幂等失效）、
> 列别名没接上（字段串位）、异常处理器没接上（500 冒充 400）、
> 现在连"防 BOM 的守卫"自己也没接上。
>
> 每一次的代码都"看起来是对的"。所以真正要养成的习惯不是"记得写守卫"，
> 而是**写完守卫之后问一句：它覆盖的范围，和我以为的一样吗？**

### 附：编辑带 BOM 的文件时的一个操作坑

我在修 `push.ps1` 时用普通文本编辑工具改它，**BOM 被去掉、中文全变成乱码、语法也坏了**
（编辑器按非 UTF-8 解码读入，再以无 BOM 写回）。
`git checkout -- push.ps1` 完整恢复后，改用
`[IO.File]::ReadAllText(path, UTF8Encoding($true))` → 替换 → `WriteAllText(path, text, UTF8Encoding($true))`
才改对。

**教训**：对带 BOM 的文件，改完必须回头验证三件事——BOM 还在、语法通过、中文没乱。
`push.ps1` 的这道守卫正是为此存在的，**所以它必须覆盖到所有 `.ps1`**（见上一条）。

### T-003：两个"测试全绿但功能是坏的"的坑（都真实发生过）

这两个坑有一个共同点，值得单独记：
**它们都是"代码看起来对、单测也全绿，但真实运行是坏的"。**
只靠单元测试发现不了，必须让测试跑在<b>真实的事务边界</b>与<b>真实的数据库</b>上。

#### 坑 1：`@Transactional` 把登录失败计数一起回滚掉了 —— 账号永远不会被锁定

| 项 | 内容 |
| --- | --- |
| **症状** | 连续输错 5 次口令，第 5 次仍然返回 401，`sys_user.failed_count` **始终是 0**。锁定功能等于没做。 |
| **根因** | 失败计数写在 `sys_user.failed_count`，而"口令错误"恰恰要抛异常。Spring 的 `@Transactional` 默认**只对 `RuntimeException` 回滚**——于是计数更新与异常一起被回滚，数据库里永远是 0。 |
| **为什么测试没发现** | 集成测试加了 `@Transactional`，MockMvc 的请求跑在**测试自己那个事务**里，业务方的"回滚"只回滚到一个 savepoint，计数在测试事务里看得见 → 测试绿。<br>**错误的事务边界同时掩盖了 bug 和它的测试。** |
| **修复** | `@Transactional(noRollbackFor = AuthException.class)`：`AuthException` 表达的是<b>预期的业务结果</b>，不是"这次操作没发生"——失败计数本身就是这次操作唯一的持久化结果，回滚掉等于什么都没做。 |
| **顺带修掉** | 移除了集成测试的 `@Transactional`，改成 `@AfterEach` 自己清理数据。这样测试跑在真实事务边界上。 |
| **防回归** | `AuthIntegrationTest.failuresShouldActuallyPersistToDatabase()`：**断言回库后的 `failed_count`**，而不是只断言 HTTP 状态码。<br>已验证：临时改回 `@Transactional` → 该测试立刻失败（`expected: 1 but was: 0`）。 |

#### 坑 2：`ON DUPLICATE KEY UPDATE` 没有唯一索引可触发 —— 演示数据每次重启都膨胀

| 项 | 内容 |
| --- | --- |
| **症状** | 文档写"10 医生 / 140 条排班"，实际库里是 **30 医生 / 420 条排班**（重启 3 次），且每重启一次就多一整套。 |
| **根因** | `data.sql` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 预置医生，但 `doctor` 表**只有主键和普通索引，没有唯一索引**——`ON DUPLICATE KEY` 永远不会触发，每次都实打实插入 10 行。<br>更严重的是连带效应：**排班是按 `doctor_id` 生成的**，10 位新医生 = 多出 140 条号源。排班自己的唯一键 `(doctor_id, work_date, period)` 兜不住，因为新医生拿到的是新的 `doctor_id`。 |
| **修复** | 给 `doctor` 加 `uk_doctor_dept_name (department_id, name)`，让 `ON DUPLICATE KEY UPDATE` 真正生效。 |
| **为什么不是 `UNIQUE(name)`** | 重名是真实存在的（"张伟"可以在两个科室各有一位），但**同一科室里出现两个同名医生**应当被视为脚本重复执行。 |
| **数据修复** | 一次性清理：保留每位 `(department_id, name)` 中 id 最小的一行，删除其余 20 行及其 280 条排班，再补建索引。**已实测重启两次，计数稳定在 10 / 140。** |

> **教训（写给下一个会话）**：
> 写完"防止 X"的代码后，要问一句 **"X 真的会发生吗？还是我把它挡住了？"**
> 这两个坑都属于同一类：保护措施没有真正接上，
> 而测试恰好绕过了保护措施本该起作用的地方。

### 环境类（Day 0 已发现）

| --- | --- | --- |
| **`npm` 被执行策略拦住** | `npm.ps1 cannot be loaded because running scripts is disabled` | **改用 `npm.cmd`**（已实测 11.16.0 可用） |

| PowerShell 控制台显示中文是乱码 | `mysql` 输出/接口返回里的中文显示成 `��ʾ����` | **只是控制台编码问题**，不是数据问题。已用 `HEX()` 与 `curl` 验证库内和响应体都是正确的 UTF-8（`E6BC94E7A4BA...` = 演示患者） |

## 与项目 1 的对照（面试可串联）

| 主题 | 项目 1 | 项目 2 |
| --- | --- | --- |
| 外部依赖失败 | AI 挂了 → 规则与人工流程不受影响 | **MQ 挂了 → 挂号仍然成功** |
| 状态机 | 审查任务 6×6 穷举 | 挂号状态机穷举 |
| 第二道防线 | 数据库触发器 + 哈希链 | **数据库唯一索引**（防重复提交） |
| 核心亮点 | 证据对齐（让 AI 错误可检测） | **防超卖**（让并发不破坏数据） |
| **踩过的坑** | "先查再改"会超卖 | **"保护措施没接上"**：事务回滚废掉锁定、缺唯一索引让幂等失效 |

> **这两个项目讲的是同一件事的两个面：**
> 项目 1 说"我不相信模型的输出"，项目 2 说"我不相信并发下的判断"。
> **都是"不相信，但用工程手段兜住"。**
>
> 而这两个坑让这句话更具体了：**"用工程手段兜住"的前提是那道手段真的接上了。**
> 唯一索引要真的存在于表上，事务边界要真的让该提交的提交——
> 否则你只是写了一段看起来像保护的代码。
