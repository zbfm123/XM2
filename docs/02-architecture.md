### 关于 Redis：号源查询缓存（Cache-Aside）

| 项 | 状态 |
| --- | --- |
| `spring-boot-starter-data-redis` | 在 |
| 用途 | **号源查询结果缓存**（`ScheduleService.listByDoctor`）|
| 缓存键 | `{#doctorId, #from, #to, #page, #size}`（Spring Cache 数组 key）|
| 失效时机 | 挂号 / 取消 / 超时取消（三处都会改号源）|
| 故障行为 | **降级为直查数据库**，功能不受影响 |

**为什么选号源查询做缓存点**：**读多写少**——所有人都在查排班，只有挂号/取消时才写。
这是缓存最经典的适用条件。

#### ⚠️ 缓存与超卖的关系（这段是重点）

**数据库永远是唯一真相，Redis 只是可丢失的加速层。**

扣减号源走的是 `ScheduleMapper.tryDeduct`——一条带条件的原子 UPDATE，
**完全不经过缓存**。所以：

- 缓存命中 → 用户可能看到一个略旧的 `remainingSlots`；
- 缓存失效 / 丢失 / 不一致 → **最坏是慢一次，绝不会多卖一个号**。

> 换句话说：**即使把 Redis 整个删掉，防超卖依然成立。**
> 缓存只允许影响"快慢"，不允许影响"对错"。这条底线有测试守着
> （`ScheduleCacheIntegrationTest` 的最后一个用例）。

#### ⚠️ 之前为什么没有用 Redis（历史，保留作为判断记录）

在接入缓存之前，这段的结论是"**引入了依赖但没用上**"。当时的理由依然成立：

1. **幂等**：靠 `idempotency_key` 唯一索引，比"Redis 记一份"更可靠；
2. **防超卖**：靠单条原子 UPDATE（D-03），刻意不用分布式锁；
3. **登录限流**：失败计数落 `sys_user.failed_count`，因为
   **锁定状态必须能扛住 Redis 重启**（否则清一次缓存就等于给攻击者重置机会）。

也就是说：**"不用它"这个判断没错，错的是"引了却不用"。**
3 天工期里没有富余去寻找真正合适的缓存场景，于是留下了一个
"在依赖列表里挂着、代码里零行"的 Redis——**那是负资产**。

2026-10-07 补上了真正合适的那一处（号源查询），这段历史保留下来，
因为它比"我用了 Redis"更能说明**有没有在想"该不该用"**。

#### 面试时这样讲

> "Redis 我是**后加的**。最初项目里引了依赖但一处没用——
> 因为幂等靠唯一索引、防超卖靠原子 UPDATE、限流落库，三件本该用 Redis 的事
> 都有更可靠的做法。**引了却不用是负资产**，我把它写在文档里当作待办。
>
> 后来补在**号源查询**上，因为它是唯一的读多写少场景。
> 但关键不是'我用了缓存'，而是**缓存不参与扣减**：
> 数据库是唯一真相，缓存坏掉最坏是慢一次，绝不会多卖一个号。
> 我还专门写了个测试，断言号源为 0 时缓存的存在不能让第二个人挂上号。"

## 四、核心设计：如何防止号源超卖

### 问题

一个专家号 20 个号源，100 人同时抢。

### 为什么"先查再改"一定超卖

```java
// ❌ 错误写法
var s = scheduleMapper.findById(id);   // 线程 A、B 都读到 remaining = 1
if (s.getRemaining() > 0) {            // A、B 都通过
    scheduleMapper.decrement(id);      // 都减 → remaining = -1
}
```

**中间那个窗口就是超卖的来源。** 加 `synchronized` 只在单机有效，
而且会把并发变成串行——**用锁掩盖问题，而不是解决问题**。

### 本项目的方案：把判断和扣减压成一条原子 SQL

```sql
UPDATE schedule
   SET remaining_slots = remaining_slots - 1
 WHERE id = #{scheduleId}
   AND remaining_slots > 0
```

```java
int affected = scheduleMapper.tryDeduct(scheduleId);
if (affected == 0) {
    // 没抢到：号源已满。**直接失败，不做任何补偿**
    throw new BusinessException(NO_SLOTS_AVAILABLE);
}
// 抢到了：affected == 1，继续建订单
```

**为什么这个方案是对的**：

| 要点 | 说明 |
| --- | --- |
| **判断和扣减在同一语句里** | 中间没有窗口，数据库的行锁保证原子性 |
| **用受影响行数回答问题** | `affected` 就是"我到底抢到没有"，不需要再查一次 |
| **失败时不需要补偿** | 没扣到就是没扣到，没有中间状态要回滚 |
| **单机多机都成立** | 依赖数据库，不依赖 JVM 锁 |

### 备选方案与为什么不选

| 方案 | 为什么不选 |
| --- | --- |
| `synchronized` / `ReentrantLock` | **只在单机有效**，多实例部署直接失效；而且把并发变串行 |
| Redisson 分布式锁 | **能用，但引入额外组件与故障点**。本项目单库即可解决，加锁是过度设计 |
| Redis 预扣减 + 异步落库 | 性能最好，但**一致性更难保证**（Redis 扣了、DB 写失败怎么办）。3 天里不值得 |
| 乐观锁（`version` 字段） | 也可行，但**高并发下重试次数多**，而本场景更适合"抢不到就明确失败" |

> **面试怎么讲**：
> "我选的是最朴素也最可靠的一条路：让数据库在一句话里完成判断和扣减。
> 我也考虑过 Redisson 分布式锁，但单库能解决的事引入额外组件，
> 多一个故障点、多一份运维成本。**我更愿意把复杂度花在真的需要的地方。**

### 第二道防线：数据库唯一索引

即使应用层判断出问题，也不允许数据不一致：

```sql
UNIQUE KEY uk_appointment_idem (idempotency_key)              -- 防重复提交
UNIQUE KEY uk_appointment_active_slot (dedup_key, schedule_id) -- 防同一人对同一排班有两个**活跃**订单
```

**应用层是"让用户看到友好提示"，唯一索引是"保证数据一定正确"。**

> ⚠️ **第二个索引不是朴素的 `(user_id, schedule_id)`，这一点踩过坑，别改回去。**
>
> 最初就是那么写的，T-007 的测试立刻暴露了它的错误：
> **"取消后无法重新挂同一个号"**——已取消的那条记录仍然占着 `(user_id, schedule_id)`，
> 数据库拒绝新建，用户看到"您已挂过该排班"，而他的号早就取消了。
>
> 正确的业务语义是"同一排班**同时只能有一个活跃订单**"，
> 而不是"历史上只能挂过一次"。所以用一列**生成列**表达：
>
> ```sql
> dedup_key BIGINT AS (IF(status = 'CANCELLED', NULL, user_id)) STORED
> ```
>
> 活跃订单 `dedup_key = user_id`（参与唯一性），已取消为 `NULL`
> （MySQL 的 UNIQUE 允许多个 NULL，天然不参与约束）。
> **"防并发重复下单"这个真正需要数据库保证的能力一点没丢**，
> 同时把"取消后可以重挂"这个正常业务路径还给了用户。
>
> 这条经验值得记住：**唯一索引约束的语义如果不是业务真正想要的，
> 它就会变成一道拦错人的防线。**

## 五、异步与延迟队列（RabbitMQ 的落点）

### 两个用途

| 用途 | 交换机/队列 | 说明 |
| --- | --- | --- |
| **挂号成功通知** | 普通队列 | 消费者写 `notification` 表 + 打日志（替代真实短信） |
| **15 分钟未支付自动取消** | **延迟队列** | 下单时发一条延迟 15 分钟的消息，到期检查并取消 |

### 关键设计：MQ 挂了不能拖垮挂号

```java
// ✅ 正确：通知失败不影响挂号
@Transactional
public Appointment book(...) {
    deductSlots(...);                    // ① 扣号源（核心，必须成功）
    var appointment = insertAppointment(...);  // ② 建订单（核心，必须成功）

    // ③ 发通知 —— 尽力而为
    try {
        mqPublisher.publishCreated(appointment);
    } catch (Exception e) {
        // 只记日志，不抛出：用户已经挂上号了，不能因为通知发不出去就失败
        log.error("挂号成功但通知投递失败，待补偿: appointmentNo={}",
                  appointment.getAppointmentNo(), e);
    }
    return appointment;
}
```

**这条纪律必须写成测试**（A-07）：把 `MqPublisher` 换成一个总是抛异常的桩，
断言**挂号依然成功**。

> 这与项目 1 的"AI 挂了规则与人工流程不受影响"是同一种思路：
> **外部依赖的失败不应该否定已经完成的业务动作。**

### 延迟队列怎么实现（RabbitMQ 3.x 没有内置延迟）

用 **TTL + 死信交换机（DLX）**：

```
appointment.delay.queue  (TTL=15min, 不消费)
        │ 消息过期
        ▼
appointment.dlx  ──→  appointment.cancel.queue  ──→  消费者：检查并取消
```

**这就是"延迟队列"的标准做法**，也是面试常问的点。文档里要画出来。

## 六、状态机

```
PENDING_PAYMENT ──支付──→ PAID ──就诊──→ COMPLETED
        │                   │
        │超时/主动取消        │主动取消
        ▼                   ▼
    CANCELLED           CANCELLED
```

**合法迁移表**（穷举测试的对象）：

| 当前 | 可迁移到 |
| --- | --- |
| `PENDING_PAYMENT` | `PAID`、`CANCELLED` |
| `PAID` | `COMPLETED`、`CANCELLED` |
| `COMPLETED` | （终态，无出边） |
| `CANCELLED` | （终态，无出边） |

**两个必须写进测试的性质**：

1. **不可自环**——否则"重复提交"可能被当成一次合法推进
2. **终态无出边**——"已完成"不能变成可取消

> 这两条与项目 1 的审查任务状态机完全同构，**可以直接对照讲**。

| **未做压测** | 并发测试验证的是**正确性**（不超卖），不是吞吐量。**不要声称高并发** |

| **消息在事务提交前发出** | 存在极小窗口：消息已投递但事务回滚。彻底解决要本地消息表 |
| ~~单体部署~~ | ✅ **已补测多实例**：两个实例共库、40 人交替打过去抢 20 号 → 全库恰好 20 单。因为依赖数据库行锁而非 JVM 锁，多实例天然成立 |

> **"未做压测"尤其要注意**：
> 并发测试证明了"不超卖"，但**没有**证明"能扛多少 QPS"。面试时不要把它说成性能数据。
>
> **"单体部署"那条原本写着"没验证过"，现在已验证并划掉。**
> ⚠️ 留着一条"没验证过"而实际上已经验证了，和留过时文档一样有害——
> 它会让人在面试里**主动说一个已经不成立的短板**。
