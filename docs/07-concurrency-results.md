## 二、数据库层证据：真实 MySQL 实测结果（2026-10-05，本机）

环境：MySQL **8.0.40** / 存储引擎 **InnoDB** / 隔离级别 **REPEATABLE-READ**
（这三项是并发行为的前提，所以记录下来；换引擎结论可能不同。）

### 验证 1：原子扣减 —— 1000 线程抢 20 个号

```
--- 验证 1：1000 个线程抢 20 个号（原子 UPDATE）---
  成功: 20   被拒: 980   剩余号源: 0
  [通过] 恰好 20 人抢到，号源恰好为 0，未超卖
```

**三条断言同时成立**：

| 断言 | 值 | 说明 |
| --- | --- | --- |
| 成功数恰好等于号源总数 | **20** | 多了就是超卖，少了就是丢号 |
| 剩余号源恰好为 0 | **0** | 不是"接近 0"，是"恰好" |
| 剩余号源不为负 | 未出现负数 | 负数余额是超卖在数据上的直接证据 |

SQL 只有一条：

```sql
UPDATE schedule
   SET remaining_slots = remaining_slots - 1
 WHERE id = ? AND remaining_slots > 0
```

### 验证 2：对照组 —— 同样的负载，但用"先查再改"的错误写法

```
--- 验证 2（对照组）：同样的 1000 线程，但用'先查再改'的错误写法 ---
  成功: 83   剩余号源: -63
  [符合预期] 错误写法超卖了：83 > 20。这反证了验证程序确实能发现问题
```

**这一项测的不是项目代码，而是"验证程序本身有没有检测能力"。**

如果程序对错误实现也报"通过"，那它给出的所有绿灯都不可信。
所以它**每次都跑一遍已知会错的写法，并且要求必须查出超卖**——查不出来才算失败。

> 这是这份记录里最值得讲的一点：
> **一条永远通过的测试和一条真能抓错的测试，在 CI 里看起来一模一样（都是绿色）。**

### 验证 3：归还号源的上界（重复取消的防线）

```
--- 验证 3：归还号源不能超过总号源（重复取消的防线）---
  扣减后: 15   归还成功次数: 5   最终: 20（总号源 20）
  [通过] 归还带上界判断，号源恰好回到 20，不会超过
```

归还语句同样带条件：

```sql
UPDATE schedule
   SET remaining_slots = remaining_slots + 1
 WHERE id = ? AND remaining_slots < total_slots   -- ⚠️ 这个条件极易被忽略
```

**如果只 `+1` 不判断上界，重复取消就会把号源加到超过总数。**
号源变多比变少更危险——它意味着数据库里的数字已经不再可信，
而"不超卖"这个保证整个建立在"`remaining_slots` 恰好等于剩余量"之上。

## 三、SQL 层证据：H2 上的回归防线

`ScheduleConcurrencyTest`（随 `mvn test` 每次运行，5 个用例）测同样的东西：

| 用例 | 断言 |
| --- | --- |
| 1000 线程抢 20 号 | 成功恰好 20、被拒 980、剩余恰好 0、无负数、总号源未被改动 |
| 号源扣光后继续扣 50 次 | 全部失败，剩余停在 0 而不是负数 |
| 对不存在的排班扣减 | 返回 0（受影响行数），不抛异常也不误判成功 |
| 归还带上界 | 扣 5 → 归还 20 次只有 5 次成功 → 恰好回到总数 |
| 并发归还 | 200 线程归还，恰好 10 次成功，剩余恰好等于总号源 |

**为什么 H2 和 MySQL 都要跑**：

> 本项目的防超卖依赖 **InnoDB 的行锁**，而 H2 用的是 MVStore 引擎，
> **锁的粒度与加锁时机都不保证与 InnoDB 一致**。
>
> - H2 那一份的价值是**可复现**：任何人 `mvn test` 就能跑，作为回归防线；
> - MySQL 那一份的价值是**真实性**：证明这条 SQL 在真正会用的数据库上确实原子。
>
> 只跑 H2 就宣称防超卖成立，是**拿一个近似实现的行为替代真实实现的行为**——
> 而这两者恰恰可能在锁上不同。

## 四点五、部署层证据：多实例（原本标注为"没实测过"）

### 为什么这一处最关键

上面表格里原本写着"多实例部署下的行为……**理论上多实例也成立**——但没实测过，不能声称"。
**这句"理论上成立"正是最需要证据的地方。**

因为：**防超卖的价值恰恰在多实例**。如果只在单实例上成立，
用 `synchronized` 就够了，根本不需要那条原子 SQL。
换句话说——**"只在单实例成立"等于这个技术内核没有价值。**

### 怎么测的

`scripts/verify-multi-instance.ps1` 起**两个后端实例**（8081 / 8082）指向**同一个库**，
然后让 40 个用户**交替打到两个实例上**抢 20 个号。

| 情形 | 预期结果 |
| --- | --- |
| 防线在 **JVM 锁**上 | 两个实例各扣各的 → **必然超卖**（各扣 20，总共 40）|
| 防线在 **数据库行锁**上（本项目的做法）| 全库只有一个赢家 → **恰好 20 单** |

### 结果

```
http://127.0.0.1:8081  成功 10   被拒 10
http://127.0.0.1:8082  成功 10   被拒 10

HTTP 200 的数量    = 20
HTTP 409 的数量    = 20
5xx 的数量        = 0
剩余号源          = 0
订单总数          = 20
下单的不同用户数    = 20
```

**多实例防超卖成立。** 两个实例各自处理了一半请求，但全库只产生了 20 条订单。

### 反向验证：证明这个测试**真的**能抓到问题

把原子扣减的 `AND remaining_slots > 0` 去掉（模拟"先查再改"），重跑：

```
http://127.0.0.1:8081  成功 20   被拒 0
http://127.0.0.1:8082  成功 20   被拒 0

HTTP 200 的数量   期望 20，实际 40
剩余号源         期望 0，实际 -20     ← 余额为负，超卖在数据上的直接证据
订单总数         期望 20，实际 40
```

**40 个请求全部成功，剩余号源 -20。** 两个实例都以为自己还有 20 个号。

> 这就是"依赖 JVM 侧判断"在多实例下的必然结果——
> 而**单实例测试永远发现不了这一点**，因为单实例下应用层判断恰好是对的。
>
> 这也说明：**一个测试能通过，不代表它能发现对应类型的错误。**
> 单实例的并发测试对"多实例超卖"是盲的。

反向验证后已 `git checkout` 完整恢复，`git diff HEAD` 无差异，重跑确认通过
（那一次两实例分到 8 / 12，总数仍是恰好 20 —— **分配比例会变，总数不会**）。

## 五、为什么不做压测（记录当时的判断）

按 `docs/04-tasks-and-acceptance.md`，**T-018 压测是"第一个被砍"的任务**：

> 并发测试（T-006）已经证明正确性，压测只是锦上添花。

这个判断的理由：

1. **本项目的技术内核是"不超卖"，不是"高吞吐"**。两者的验证手段完全不同：
   前者用正确性断言（恰好 20 单），后者用统计指标（P99 延迟、TPS）。
2. 做压测需要引入 JMeter/wrk 等工具、设计压测场景、分析结果——
   **而这些时间花在"把可靠性细节做对"上更值钱**（见面试问答里"如果再给两天"那一问）。
3. 更重要的：**说错话的成本高于不说的成本**。
   把并发正确性包装成性能数据，被追问一句"P99 多少"就露馅了。
