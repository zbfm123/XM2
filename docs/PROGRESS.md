### ⚠️ 剩下一步：服务化（需要管理员权限）

当前 broker 是**独立进程**，重启机器后不会自动运行。注册 Windows 服务必须提权，所以这一步留给用户：

```powershell
# 以管理员身份运行 PowerShell，然后：
powershell -ExecutionPolicy Bypass -File D:\xmdeepseek\hospital-appointment\scripts\install-rabbitmq-service.ps1
```

脚本做的事：写系统级环境变量 → 停旧实例 → `rabbitmq-service install` →
**改成自动启动**（`sc config`，与 MySQL80 / Redis 一致）→ 启动 → 启用管理插件 → 验证并打印结果。
**幂等，可重复执行。**

> 脚本里最值得说明的一处设计：**用 `RABBITMQ_ERLANG_COOKIE` 固定 cookie 值**。
> 原因是踩了一个真实的坑（见下）。本地开发用已知值可以接受，
> 但**生产环境绝不该这样做**——正式环境应让 RabbitMQ 随机生成 cookie 并控制文件权限。脚本注释里写明了这一点。

### 踩坑：MQ 安装本身就有 4 个坑

| 坑 | 症状 | 根因与处理 |
| --- | --- | --- |
| **`RABBITMQ_LOGS` 指向目录** | broker 启动即崩，`Slogan: cannot_log_to_file, "d:/rabbitmq/data/log", eisdir` | 它要的是**日志文件路径**，不是目录。`erl_crash.dump` 里的 Slogan 是定位这类崩溃最快的入口 |
| **Erlang 在 Windows 不认 `HOME`** | `Failed to create cookie file 'd:/Users/tianliang/.erlang.cookie': enoent`——路径被拼坏 | 我一开始设 `HOMEDRIVE`+`HOME`，无效。用 `init:get_argument(home)` 探查才发现 **Erlang 读的是 `USERPROFILE`** |
| **服务与 CLI 的用户配置文件不同** | 服务以 LocalSystem 跑（cookie 在 `systemprofile`），你终端跑 CLI（cookie 在 `C:\Users\你`）→ **CLI 报连不上，而服务其实好好的** | 用 `RABBITMQ_ERLANG_COOKIE` 显式固定同一个值，两边都不再依赖配置文件路径。**这是"看起来像 MQ 坏了、其实是认证文件不匹配"的典型误判** |
| **`escript` 遇到 UTF-8 BOM 会挂** | `syntax error before ':'` | escript 要**无 BOM**；而 PowerShell 脚本**必须带 BOM**。同一台机器上两个相反的规矩，别搞混 |

> 还有一个顺手修掉的：Erlang 崩溃时把 `erl_crash.dump`（1MB+）写在**当前工作目录**，
> 污染了 `D:\xmdeepseek`。已设 `ERL_CRASH_DUMP` 指到固定位置。**项目 1 也踩过这个坑。**

### T-004：三个缺陷，全部由新写的测试当场抓出来

这一轮值得记的不是"写了什么功能"，而是**新测试第一次跑就红了 3 条**——
三条都是真问题，只是每一条的"性质"不同：

| # | 症状 | 性质 | 根因与修复 |
| --- | --- | --- | --- |
| 1 | `departmentName` 显示成了**医生名** | **静默的数据串位**（最危险的一类） | JOIN 里医生表和科室表**都有 `name` 列**，结果集出现两个同名标签，构造器映射选错了列——**而且不报错**。修复：每个列显式起别名，别名 = record 字段名，让映射变成按名字而不是按位置 |
| 2 | 缺 `deptId` 时返回 **500** | **状态码归错责任方** | 少一个 `@ExceptionHandler(MissingServletRequestParameterException.class)`，异常掉进兜底变成"服务器内部错误"。**调用方少传参数，却让前端去查服务端日志**。已补：400 + `INVALID_PARAMETER` |
| 3 | 分页响应里**没有 `totalPages`** | **序列化漏字段** | Jackson 只把 `getXxx()` 当属性，`record` 内自定义的 `totalPages()` 默认不序列化。前端拿不到总页数，分页器只能显示"上一页/下一页"。已补 `@JsonProperty("totalPages")` |

> **这三条都不是"功能没做完"，而是"功能看起来做完了但结果是错的"**——
> 和 T-003 那两个坑同一类。共同点：<b>编译器不会报错，只有断言会。</b>
> 结论仍然是那句：写完一个查询，要用测试去断言**取回来的每个字段到底是什么**，
> 而不是只断言"HTTP 200 且 list 非空"。

**第 1 条特别值得讲**（面试也是一个好例子）：
两个表有同名列 + 靠位置映射 = 一条不会报错的错误。
它的表现（"科室名那一栏是医生名"）和它的原因（SQL 列标签歧义）之间的距离非常远，
**如果没有断言具体字段值，它会一路活到演示现场**。

### 附：编辑带 BOM 的文件时的一个操作坑

我在修 `push.ps1` 时用普通文本编辑工具改它，**BOM 被去掉、中文全变成乱码、语法也坏了**
（编辑器按非 UTF-8 解码读入，再以无 BOM 写回）。
`git checkout -- push.ps1` 完整恢复后，改用
`[IO.File]::ReadAllText(path, UTF8Encoding($true))` → 替换 → `WriteAllText(path, text, UTF8Encoding($true))`
才改对。

**教训**：对带 BOM 的文件，改完必须回头验证三件事——BOM 还在、语法通过、中文没乱。
`push.ps1` 的这道守卫正是为此存在的，**所以它必须覆盖到所有 `.ps1`**（见上一条）。

### T-003：两个"测试全绿但功能是坏的"的坑（都真实发生过）

这两个坑有一个共同点，值得单独记：
**它们都是"代码看起来对、单测也全绿，但真实运行是坏的"。**
只靠单元测试发现不了，必须让测试跑在<b>真实的事务边界</b>与<b>真实的数据库</b>上。

#### 坑 1：`@Transactional` 把登录失败计数一起回滚掉了 —— 账号永远不会被锁定

| 项 | 内容 |
| --- | --- |
| **症状** | 连续输错 5 次口令，第 5 次仍然返回 401，`sys_user.failed_count` **始终是 0**。锁定功能等于没做。 |
| **根因** | 失败计数写在 `sys_user.failed_count`，而"口令错误"恰恰要抛异常。Spring 的 `@Transactional` 默认**只对 `RuntimeException` 回滚**——于是计数更新与异常一起被回滚，数据库里永远是 0。 |
| **为什么测试没发现** | 集成测试加了 `@Transactional`，MockMvc 的请求跑在**测试自己那个事务**里，业务方的"回滚"只回滚到一个 savepoint，计数在测试事务里看得见 → 测试绿。<br>**错误的事务边界同时掩盖了 bug 和它的测试。** |
| **修复** | `@Transactional(noRollbackFor = AuthException.class)`：`AuthException` 表达的是<b>预期的业务结果</b>，不是"这次操作没发生"——失败计数本身就是这次操作唯一的持久化结果，回滚掉等于什么都没做。 |
| **顺带修掉** | 移除了集成测试的 `@Transactional`，改成 `@AfterEach` 自己清理数据。这样测试跑在真实事务边界上。 |
| **防回归** | `AuthIntegrationTest.failuresShouldActuallyPersistToDatabase()`：**断言回库后的 `failed_count`**，而不是只断言 HTTP 状态码。<br>已验证：临时改回 `@Transactional` → 该测试立刻失败（`expected: 1 but was: 0`）。 |

#### 坑 2：`ON DUPLICATE KEY UPDATE` 没有唯一索引可触发 —— 演示数据每次重启都膨胀

| 项 | 内容 |
| --- | --- |
| **症状** | 文档写"10 医生 / 140 条排班"，实际库里是 **30 医生 / 420 条排班**（重启 3 次），且每重启一次就多一整套。 |
| **根因** | `data.sql` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 预置医生，但 `doctor` 表**只有主键和普通索引，没有唯一索引**——`ON DUPLICATE KEY` 永远不会触发，每次都实打实插入 10 行。<br>更严重的是连带效应：**排班是按 `doctor_id` 生成的**，10 位新医生 = 多出 140 条号源。排班自己的唯一键 `(doctor_id, work_date, period)` 兜不住，因为新医生拿到的是新的 `doctor_id`。 |
| **修复** | 给 `doctor` 加 `uk_doctor_dept_name (department_id, name)`，让 `ON DUPLICATE KEY UPDATE` 真正生效。 |
| **为什么不是 `UNIQUE(name)`** | 重名是真实存在的（"张伟"可以在两个科室各有一位），但**同一科室里出现两个同名医生**应当被视为脚本重复执行。 |
| **数据修复** | 一次性清理：保留每位 `(department_id, name)` 中 id 最小的一行，删除其余 20 行及其 280 条排班，再补建索引。**已实测重启两次，计数稳定在 10 / 140。** |

> **教训（写给下一个会话）**：
> 写完"防止 X"的代码后，要问一句 **"X 真的会发生吗？还是我把它挡住了？"**
> 这两个坑都属于同一类：保护措施没有真正接上，
> 而测试恰好绕过了保护措施本该起作用的地方。

## 与项目 1 的对照（面试可串联）

| 主题 | 项目 1 | 项目 2 |
| --- | --- | --- |
| 外部依赖失败 | AI 挂了 → 规则与人工流程不受影响 | **MQ 挂了 → 挂号仍然成功** |
| 状态机 | 审查任务 6×6 穷举 | 挂号状态机穷举 |
| 第二道防线 | 数据库触发器 + 哈希链 | **数据库唯一索引**（防重复提交） |
| 核心亮点 | 证据对齐（让 AI 错误可检测） | **防超卖**（让并发不破坏数据） |
| **踩过的坑** | "先查再改"会超卖 | **"保护措施没接上"**：事务回滚废掉锁定、缺唯一索引让幂等失效 |

> **这两个项目讲的是同一件事的两个面：**
> 项目 1 说"我不相信模型的输出"，项目 2 说"我不相信并发下的判断"。
> **都是"不相信，但用工程手段兜住"。**
>
> 而这两个坑让这句话更具体了：**"用工程手段兜住"的前提是那道手段真的接上了。**
> 唯一索引要真的存在于表上，事务边界要真的让该提交的提交——
> 否则你只是写了一段看起来像保护的代码。
