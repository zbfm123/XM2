## 三、数据模型

6 张表，够用且不臃肿。

```
sys_user            用户（患者）
department          科室
doctor              医生（属于科室）
schedule            排班（医生 + 日期 + 时段 + 号源）  ← 防超卖发生在这里
appointment         挂号订单（患者 + 排班 + 状态）      ← 状态机在这里
notification        通知记录（异步消费的产物）
```

### 关键字段

**`schedule`（号源）**

| 字段 | 说明 |
| --- | --- |
| `doctor_id` / `work_date` / `period` | `period` = `AM` / `PM`，三者唯一索引（防重复排班） |
| `total_slots` | 总号源 |
| `remaining_slots` | **剩余号源——并发扣减的对象** |
| `fee` | 挂号费 |

**`appointment`（挂号订单）**

| 字段 | 说明 |
| --- | --- |
| `appointment_no` | 业务单号（对外展示，不暴露自增 id） |
| `idempotency_key` | **幂等键**，唯一索引 |
| `status` | 见状态机 |
| `expire_at` | 待支付过期时间，配合延迟队列 |
| `user_id` + `schedule_id` | **唯一索引**（防重复挂号） |

> ⚠️ **两个唯一索引是本项目的"第二道防线"**：
> `idempotency_key` 防重复提交，`(user_id, schedule_id)` 防同一人抢两个号。
> 应用层的判断可能被并发绕过，**唯一索引不会被绕过**。

## 四、核心设计：如何防止号源超卖

### 问题

一个专家号 20 个号源，100 人同时抢。

### 为什么"先查再改"一定超卖

```java
// ❌ 错误写法
var s = scheduleMapper.findById(id);   // 线程 A、B 都读到 remaining = 1
if (s.getRemaining() > 0) {            // A、B 都通过
    scheduleMapper.decrement(id);      // 都减 → remaining = -1
}
```

**中间那个窗口就是超卖的来源。** 加 `synchronized` 只在单机有效，
而且会把并发变成串行——**用锁掩盖问题，而不是解决问题**。

### 本项目的方案：把判断和扣减压成一条原子 SQL

```sql
UPDATE schedule
   SET remaining_slots = remaining_slots - 1
 WHERE id = #{scheduleId}
   AND remaining_slots > 0
```

```java
int affected = scheduleMapper.tryDeduct(scheduleId);
if (affected == 0) {
    // 没抢到：号源已满。**直接失败，不做任何补偿**
    throw new BusinessException(NO_SLOTS_AVAILABLE);
}
// 抢到了：affected == 1，继续建订单
```

**为什么这个方案是对的**：

| 要点 | 说明 |
| --- | --- |
| **判断和扣减在同一语句里** | 中间没有窗口，数据库的行锁保证原子性 |
| **用受影响行数回答问题** | `affected` 就是"我到底抢到没有"，不需要再查一次 |
| **失败时不需要补偿** | 没扣到就是没扣到，没有中间状态要回滚 |
| **单机多机都成立** | 依赖数据库，不依赖 JVM 锁 |

### 备选方案与为什么不选

| 方案 | 为什么不选 |
| --- | --- |
| `synchronized` / `ReentrantLock` | **只在单机有效**，多实例部署直接失效；而且把并发变串行 |
| Redisson 分布式锁 | **能用，但引入额外组件与故障点**。本项目单库即可解决，加锁是过度设计 |
| Redis 预扣减 + 异步落库 | 性能最好，但**一致性更难保证**（Redis 扣了、DB 写失败怎么办）。3 天里不值得 |
| 乐观锁（`version` 字段） | 也可行，但**高并发下重试次数多**，而本场景更适合"抢不到就明确失败" |

> **面试怎么讲**：
> "我选的是最朴素也最可靠的一条路：让数据库在一句话里完成判断和扣减。
> 我也考虑过 Redisson 分布式锁，但单库能解决的事引入额外组件，
> 多一个故障点、多一份运维成本。**我更愿意把复杂度花在真的需要的地方。**"

### 第二道防线：数据库唯一索引

即使应用层判断出问题，也不允许数据不一致：

```sql
UNIQUE KEY uk_appointment_idem (idempotency_key)      -- 防重复提交
UNIQUE KEY uk_appointment_user_schedule (user_id, schedule_id)  -- 防同一人抢两个号
```

**应用层是"让用户看到友好提示"，唯一索引是"保证数据一定正确"。**

## 五、异步与延迟队列（RabbitMQ 的落点）

### 两个用途

| 用途 | 交换机/队列 | 说明 |
| --- | --- | --- |
| **挂号成功通知** | 普通队列 | 消费者写 `notification` 表 + 打日志（替代真实短信） |
| **15 分钟未支付自动取消** | **延迟队列** | 下单时发一条延迟 15 分钟的消息，到期检查并取消 |

### 关键设计：MQ 挂了不能拖垮挂号

```java
// ✅ 正确：通知失败不影响挂号
@Transactional
public Appointment book(...) {
    deductSlots(...);                    // ① 扣号源（核心，必须成功）
    var appointment = insertAppointment(...);  // ② 建订单（核心，必须成功）

    // ③ 发通知 —— 尽力而为
    try {
        mqPublisher.publishCreated(appointment);
    } catch (Exception e) {
        // 只记日志，不抛出：用户已经挂上号了，不能因为通知发不出去就失败
        log.error("挂号成功但通知投递失败，待补偿: appointmentNo={}",
                  appointment.getAppointmentNo(), e);
    }
    return appointment;
}
```

**这条纪律必须写成测试**（A-07）：把 `MqPublisher` 换成一个总是抛异常的桩，
断言**挂号依然成功**。

> 这与项目 1 的"AI 挂了规则与人工流程不受影响"是同一种思路：
> **外部依赖的失败不应该否定已经完成的业务动作。**

### 延迟队列怎么实现（RabbitMQ 3.x 没有内置延迟）

用 **TTL + 死信交换机（DLX）**：

```
appointment.delay.queue  (TTL=15min, 不消费)
        │ 消息过期
        ▼
appointment.dlx  ──→  appointment.cancel.queue  ──→  消费者：检查并取消
```

**这就是"延迟队列"的标准做法**，也是面试常问的点。文档里要画出来。

## 六、状态机

```
PENDING_PAYMENT ──支付──→ PAID ──就诊──→ COMPLETED
        │                   │
        │超时/主动取消        │主动取消
        ▼                   ▼
    CANCELLED           CANCELLED
```

**合法迁移表**（穷举测试的对象）：

| 当前 | 可迁移到 |
| --- | --- |
| `PENDING_PAYMENT` | `PAID`、`CANCELLED` |
| `PAID` | `COMPLETED`、`CANCELLED` |
| `COMPLETED` | （终态，无出边） |
| `CANCELLED` | （终态，无出边） |

**两个必须写进测试的性质**：

1. **不可自环**——否则"重复提交"可能被当成一次合法推进
2. **终态无出边**——"已完成"不能变成可取消

> 这两条与项目 1 的审查任务状态机完全同构，**可以直接对照讲**。

## 七、关键决策记录

| 编号 | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| D-01 | **不做微服务**，模块化单体 | Spring Cloud 拆分 | 3 天内拆分只会得到"能启动但跑不通"的东西；且**没系统学过**，面试深挖就露馅 |
| D-02 | **不做管理端**，数据用 SQL 预置 | 完整增删改查 | 管理端最耗时、零技术深度，是 3 天里最该砍的 |
| D-03 | 防超卖用**原子 UPDATE**，不用分布式锁 | Redisson | 单库能解决就不引额外组件；**多的组件就是多的故障点** |
| D-04 | 用**唯一索引**做第二道防线 | 只靠应用层判断 | 应用层判断可能被并发绕过，唯一索引不会 |
| D-05 | **失效用 TTL + 死信交换机**，不用延迟插件 | `rabbitmq_delayed_message_exchange` | 插件需要额外安装；DLX 是标准做法且**面试更常问** |
| D-06 | **挂号成功但通知失败不能让挂号失败** | 同一事务里发消息 | 外部依赖抖动不应否定已完成的业务动作（与项目 1 的降级同构） |
| D-07 | 挂号的"支付"用**模拟回调**，不接真实支付 | 支付宝/微信沙箱 | 联调成本 > 收益；**消费者逻辑完全一致**，不影响展示 |
| D-08 | 前端**只用 Vue 最基础的能力** | Pinia / 自定义指令 / TS | 用户只看过教程没独立写过；**能跑通 > 用全** |
| D-09 | JWT 鉴权**直接复用项目 1 的做法** | 重新设计 | 已验证过的东西不重新发明 |
| D-10 | 端口：后端 **8081**，前端 dev **5173**，Nginx **80** | 复用 8080 | 避免与项目 1 冲突，**两个项目可以同时起** |

## 八、已知限制（提前写，面试主动交代）

| 限制 | 说明 |
| --- | --- |
| **通知不是真实短信** | 写库 + 日志。消费者逻辑与真实场景一致，替换实现即可 |
| **支付是模拟的** | 没有第三方对接 |
| **没有管理端** | 数据靠 SQL 预置，属主动范围决策 |
| **未做鉴权细分** | 只有"登录用户"一种角色，没有 RBAC |
| **未做压测** | 并发测试验证的是**正确性**（不超卖），不是吞吐量。**不要声称高并发** |
| **单体部署** | 无多实例，因此没验证过分布式场景下的锁行为（因为压根没用锁） |

> 最后一条尤其要注意：**并发测试证明了"不超卖"，但没有证明"能扛多少 QPS"。**
> 面试时不要把它说成性能数据。
