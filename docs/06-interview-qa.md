> "我做了两个项目，刻意选了不重叠的方向。

## 一、核心亮点：防止号源超卖（必问，要能讲 3 分钟）

### Q1：怎么防止超卖？

**先讲错误写法**（这比直接讲答案更有说服力）：

```java
// ❌ 经典的超卖
var s = scheduleMapper.selectById(id);   // 线程 A、B 都读到 remaining = 1
if (s.getRemainingSlots() > 0) {         // A、B 都通过这道判断
    scheduleMapper.decrement(id);         // 都减 → remaining = -1
}
```

**再讲做法**——把判断和扣减压成一条语句：

```sql
UPDATE schedule
   SET remaining_slots = remaining_slots - 1
 WHERE id = #{scheduleId}
   AND remaining_slots > 0
```

```java
int affected = scheduleMapper.tryDeduct(scheduleId);
if (affected == 0) {                     // 受影响行数就是答案
    throw new BusinessException(NO_SLOTS_AVAILABLE, "该时段号源已约满");
}
```

三个要点：

| 要点 | 说明 |
| --- | --- |
| **判断和扣减在同一语句** | 中间没有窗口，由数据库行锁保证原子性 |
| **用受影响行数回答"抢到没有"** | 不需要再查一次库，也不靠异常判断 |
| **失败不补偿** | 没扣到就是没扣到，没有中间状态要回滚 |

### Q2：证据呢？（**这题必须答得出来**）

**两处独立证据**，我的测试就在仓库里：

| 环境 | 结果 |
| --- | --- |
| H2（`ScheduleConcurrencyTest`，`mvn test` 就能跑） | 1000 线程抢 20 号 → 成功恰好 **20**、剩余恰好 **0**、无负数 |
| **真实 MySQL 8.0.40 / InnoDB**（`scripts/verify-concurrency-on-mysql.ps1`） | 成功 **20**、被拒 **980**、剩余 **0** |

**为什么两处都要**：防超卖依赖的是 **InnoDB 的行锁**，而 H2 的锁实现与它不同。
只跑 H2 是拿一个近似实现的行为替代真实实现——**这两者恰恰可能在锁上不同**。

### Q3：你怎么知道你的并发测试真的有效？

**这题是分水岭**。多数人的并发测试其实什么都没验证。我做了**反向验证**：

故意把实现换成"先查再改"，然后跑同一个测试：

| 验证对象 | 结果 |
| --- | --- |
| H2 测试 | **失败**：`expected: 20 but was: 64`（超卖 3 倍多） |
| MySQL 验证程序 | **超卖 63 个**（成功 83 / 剩余 -63） |

而且 MySQL 那个程序里**永久保留了这个错误实现作为对照组**，每次都跑，
并且**要求它必须查出超卖**——查不出来才算失败。

> 一句话总结：**一条永远通过的测试和一条真能抓错的测试，在 CI 里看起来一模一样（都是绿色）。**
> 只有把它对着已知错误跑一次，才知道自己修的不是"测试没报错"，而是"代码真的对"。

### Q4：为什么不用分布式锁 / Redisson？

> "我考虑过。但**单库的原子 UPDATE 已经能保证正确性**，
> 引入 Redisson 只是多一个组件、多一个故障点——
> 而且它把并发变成了串行，是用锁掩盖问题，不是解决问题。
> 我更愿意把复杂度花在真的需要的地方。"

**加分点**：主动说清它什么时候才需要——

> "如果将来号源拆分到多个库、或者要跨服务扣减，那单条 SQL 就不够了，
> 那时才需要分布式锁或事务消息。**判断依据是'是否跨进程'，不是'并发高不高'。**"

### Q5：号源扣减有没有做缓存（Redis）？

> "没有，而且我认为这里不该做。号源是**强一致**数据：
> Redis 扣了、DB 写失败怎么办？这就是典型的一致性问题。
> 本项目单库单表、量级也不高，**数据库的行锁完全够用**。
> Redis 我用在了更合适的地方——测试里替代令牌黑名单/幂等缓存。"

## 二、第二个亮点：MQ 挂了挂号仍然成功（必问）

### Q6：MQ 出问题会不会影响用户挂号？

**答"不会"，然后立刻给证据**：

```java
// ① 业务动作先完成
int deducted = scheduleMapper.tryDeduct(scheduleId);   // 扣号源
appointmentMapper.insert(appointment);                 // 建订单

// ② 通知是"尽力而为"，失败只记日志
boolean notified = tryNotifyBooked(appointment, schedule);   // 内部 catch 一切
if (!notified) {
    log.error("挂号成功但通知投递失败（业务不受影响，待补偿）: no={}", ...);
}
// 返回给用户的仍然是"挂号成功"
```

**证据**：`MqUnavailableDoesNotBreakBookingTest` 用一个**所有方法都抛异常**的桩替换通知实现，
断言四件事：订单建立、号源扣减、**业务确实尝试过投递**、以及**没有通知记录**。

最后一条最关键：它证明"测试通过"不是因为通知其实发成功了，而是**投递确实失败、但业务照常**。

### Q7：这个坑有什么实际危害？

> "很多人做 MQ 会把'发消息'和'主事务'绑在一起，结果 MQ 一抖动用户就挂不上号——
> 而用户根本不在乎通知发没发出去，**他只想挂上号**。
> 外部依赖的失败，不应该否定已经完成的业务动作。"

**可以串到项目 1**：

> "这和项目 1 的'AI 挂了，规则结论与人工复核流程不受影响'是**同一种纪律**。
> 我在两个项目里都把它写成了测试，因为这种解耦**很容易在后续改动里被悄悄破坏**。"

### Q8：那你为什么还留了第二层兜底？不是多余吗？

**这是我被自己测试打脸后补上的，讲出来很加分**：

> "接口上写着'绝不抛异常'，但那只是一条**约定**，而约定靠人遵守、人会漏。
> 我的测试用'总是抛异常'的桩时，挂号**立刻被打挂了**——说明只有第一层不够。
> 所以调用方也加了一层 catch。
> **A-07 因此从'取决于实现者记得 catch'变成'无论实现怎么写都成立'。**"

## 三、状态机与穷举测试（工程纪律）

### Q9：状态机怎么设计的？

**把迁移关系写成"数据"，而不是散落在 if/switch 里**：

```java
m.put(PENDING_PAYMENT, EnumSet.of(PAID, CANCELLED));
m.put(PAID,            EnumSet.of(COMPLETED, CANCELLED));
m.put(COMPLETED,       EnumSet.noneOf(AppointmentStatus.class));   // 终态
m.put(CANCELLED,       EnumSet.noneOf(AppointmentStatus.class));
```

**为什么这样写**：这样"合法迁移关系"才成为**可被穷举断言的对象**。
写在 if 里的话，你连"要测哪些组合"都说不清。

### Q10：穷举测试怎么写才不会自欺欺人？

**这题我问过自己，答案是**：**预期表必须独立写一遍，不能从实现里读出来**。

错误写法（同义反复，实现错了测试照样绿）：

```java
assertThat(from.canTransitionTo(to))
    .isEqualTo(from.allowedTargets().contains(to));   // ❌ 两边来自同一个实现
```

我的做法：测试里的预期表是**照着架构文档的状态机图手写的第二份定义**，
两处独立描述必须一致。4 个状态 × 4 个状态 = **16 个组合逐一断言**。

两条不变量各有独立测试：

| 不变量 | 为什么必须 |
| --- | --- |
| **不可自环** | 否则"重复提交同一个状态变更"会被当成一次合法推进，而实际上什么都没发生 |
| **终态无出边** | 否则"已完成的挂号还能被取消"，而号源已经消耗掉了 |

同样做了**反向验证**：植入"自环 + 终态可取消"，**8 条测试立刻失败**。

### Q11：合法迁移只有 4 条，非法有 12 条——这说明什么？

> "说明**穷举是必要的**。如果我只测那 4 条合法路径，
> 剩下 12 条里任何一条被误判为合法我都发现不了。
> 而这类 bug 的表现是'接口返回成功、状态看起来也对'，最难查。"

## 四、幂等（很容易被追问的地方）

### Q12：幂等怎么做的？

**三层**，讲清哪层是体验、哪层才是保证：

| 层 | 手段 | 挡住什么 |
| --- | --- | --- |
| ① 前端 | 按钮 loading 期间禁用 | 绝大多数双击 |
| ② 前端 | 同一排班复用同一个幂等键 | "请求发出去了但响应没回来，用户又点一次" |
| ③ **后端** | `idempotency_key` **唯一索引** | 前两层都被绕过的情况 |

> **前端这两层是体验，后端那一层才是保证。**
> 应用层的判断可能被并发绕过，**唯一索引不会被绕过**。

### Q13：幂等键为什么必须由客户端提供？

> "因为'这两次请求是不是同一个意图'**只有客户端知道**。
> 如果做成可选（不传就不去重），那防重复提交就变成**依赖客户端自觉**的功能——
> 而客户端恰恰最不可控（用户双击、网络重试、前端重试逻辑写错都发生在这里）。
> 我把它设为**必填**，等于要求客户端显式回答'我怎么知道这两次是同一件事'。"

### Q14：取消挂号要注意什么？

**两个细节，都是"不写测试就发现不了"的**：

1. **重复取消必须幂等**：用户第二次点取消时目标已达成，返回 409 只会让前端多写一个无意义分支。
   （我第一版就是返回 409，被 A-05 的测试抓出来了。）
2. **归还号源必须带上界判断**：

```sql
UPDATE schedule SET remaining_slots = remaining_slots + 1
 WHERE id = ? AND remaining_slots < total_slots   -- ⚠️ 这个条件极易被忽略
```

> "**如果只 +1 不判断上界，重复取消就会把号源加到超过总数。**
> 号源变多比变少更危险——它意味着数据库里的数字已经不再可信，
> 而'不超卖'这个保证整个建立在'remaining 恰好等于剩余量'之上。"

## 五、数据库设计（被追问时用）

### Q15：`(user_id, schedule_id)` 唯一索引，这样对吗？

**这题我踩过，讲出来最有说服力**：

> "我最初就是这么写的，测试立刻告诉我它错了：
> **'取消后无法重新挂同一个号'**——已取消的那条记录仍然占着 `(user_id, schedule_id)`，
> 数据库拒绝新建，用户看到'您已挂过该排班'，而他的号早就取消了。
>
> 正确的业务语义是'同一排班**同时只能有一个活跃订单**'，
> 而不是'历史上只能挂过一次'。所以我改用一列**生成列**表达：
>
> ```sql
> dedup_key BIGINT AS (IF(status = 'CANCELLED', NULL, user_id)) STORED,
> UNIQUE KEY uk_appointment_active_slot (dedup_key, schedule_id)
> ```
>
> 活跃订单 `dedup_key = user_id`（参与唯一性），已取消为 `NULL`
> （MySQL 的 UNIQUE 允许多个 NULL，天然不参与约束）。
> **防并发重复下单的能力一点没丢，同时把'取消后可以重挂'还给了用户。**"

**结论句**（值得背下来）：

> "**唯一索引约束的语义如果不是业务真正想要的，它就会变成一道拦错人的防线。**"

### Q16：为什么有两个唯一索引？

> "它们是**第二道防线**：`idempotency_key` 防重复提交，`active_slot` 防同一人抢两个号。
> 应用层负责给用户友好提示，唯一索引负责保证数据一定正确。"

## 六、延迟队列（A-06，容易讲得浅）

### Q17：15 分钟未支付自动取消，怎么实现的？

**先说清机制**（这是面试常问点）：

```
下单 ──→ appointment.delay.exchange ──→ appointment.delay.queue
                                          (TTL 15min，**故意没有消费者**)
                                               │ TTL 到期成为死信
                                               ▼
                                        appointment.dlx ──→ appointment.cancel.queue
                                                                  ──→ 消费者检查状态 → 取消 + 归还号源
```

> "**RabbitMQ 没有内置延迟队列。** 我用 TTL + 死信交换机实现：
> 消息先进一个**没有消费者**的队列，等它过期，过期后由 broker 按死信配置转发到取消队列。
> 关键点是**那个队列自己不消费**——没有消费者，消息就只能等到过期。"

**为什么不用延迟插件**：需要额外安装与运维，而 DLX 是标准机制、面试更常问。

### Q18：这个设计最大的坑是什么？

**这是本题的分水岭**——多数人答不出：

> "延迟消息是**下单那一刻**发出去的，15 分钟后才回来，而这 15 分钟里用户可能**已经付款**了。
> 如果消费者不看状态就取消：
>
> ```
> 13:00  下单，发一条 15 分钟延迟消息
> 13:05  用户支付成功 -> PAID
> 13:15  延迟消息到期 -> 把 PAID 改成 CANCELLED 并归还号源
> ```
>
> 结果是**用户付了钱、号被取消、号源还被卖给了别人**——同时伤害用户和医院的账。"

**所以**：取消动作必须用**带起始状态条件的原子 UPDATE**（`WHERE status = 'PENDING_PAYMENT'`），
受影响行数为 0 说明"它已经不是我该取消的那个状态了"，此时**什么都不做**。

**结论句**：

> "**延迟消息只能表达'到了该检查的时间'，不能表达'到点就该执行'。**
> 到点之后该做什么，必须重新判断一次。"

已写成测试：下单 → 手工推进到 `PAID` → 等超过 TTL → 断言仍是 `PAID` 且号源未归还。

## 六点五、支付与"为什么到得了 PAID"（会被追问）

### Q18.5：你的支付是怎么做的？为什么有个 `/pay` 接口？

**这题要答出"我知道它是模拟的，以及真实系统该长什么样"**：

> "支付我是**主动砍掉**的（决策 D-07）：接支付宝/微信沙箱的联调成本大于收益，
> 而消费者逻辑完全一致，替换实现即可。
>
> 但我保留了**模拟回调入口** `POST /api/appointments/{no}/pay`，
> 这一步是补上的——最初我看任务书里没有支付任务就没做，
> 结果发现 **`PAID` 与 `COMPLETED` 在接口层完全不可达**，
> 只有测试手动改数据库才能到。
>
> 后果不只是'状态机有两条路径亮不起来'，更要紧的是：
> **'已支付的订单不会被超时误取消'这条演示不出来**——
> 因为我没有入口去制造'已支付'这个场景。而那是 A-06 里最关键的那个判断。"

**接着主动说清它的边界**：

> "⚠️ 这个端点**真实系统里绝不能长这样**：必须校验支付平台的签名与金额，
> 否则任何人构造一个请求就能把订单标记成已支付。
> 我在代码注释里写明了这一点，命名上也直接叫 `pay`（模拟），
> 避免它被误当成一个可以上线的接口。"

### Q18.6：两个状态推进为什么不写两个方法？

> "因为**执行结构完全相同**：带起始状态的原子 UPDATE、
> 受影响行数为 0 说明状态已被别人改过、只做通知不做补偿。
> 写两份会复制这个结构，将来改一处忘一处。
>
> 更重要的是：合法性**只由状态机的 `canTransitionTo` 裁决**，
> 我没有在 Controller 里重新实现一遍规则。
> 所以它天然就做到了不能跳步、**终态不可被回调复活**、不可自环——
> 这三条本来就被穷举测试守着，规则只有一份。"

### Q18.7：如果一个已取消的订单收到"支付成功"回调怎么办？

**这是个陷阱问题，答对了很加分**：

> "**必须拒绝。** `CANCELLED` 是终态，无出边。
> 状态机的 `canTransitionTo` 会返回 false，接口回 409 `INVALID_STATE`，
> 订单状态保持不变。
>
> 真实场景里这确实会发生：用户在支付页停留很久，
> 订单被超时取消了，然后他才点了确认付款。这时正确做法是
> **拒绝这次回调并触发退款**，而不是把订单从'已取消'改回'已支付'——
> 因为那个号源可能已经卖给别人了。
>
> 这一条我有测试：`AppointmentLifecycleIntegrationTest.terminalStateCannotBeRevived`。"

## 七、你知道这个项目的边界吗（主动交代，显得成熟）

### Q19：这个项目有什么没做/做不到的？

**主动说，不要等对方问出来**：

| 限制 | 说明 |
| --- | --- |
| **通知不是真实短信** | 写库 + 日志。消费者逻辑与真实场景一致，替换实现即可 |
| **支付是模拟的** | 没有第三方对接（决策 D-07） |
| **没有管理端** | 数据靠 SQL 预置，属主动范围决策——管理端最耗时、零技术深度 |
| **没有 RBAC** | 只有"登录用户"一种角色 |
| **未做压测** | ⚠️ **并发测试证明的是正确性（不超卖），不是吞吐量。不要声称高并发** |
| **单体部署** | 无多实例，因此没验证过分布式场景下的锁行为（因为压根没用锁） |
| **消息在事务提交前发出** | 存在极小窗口：消息已投递但事务回滚。彻底解决要本地消息表，本期时间不允许 |
| **登录限流只按账号** | 不按 IP。撞库攻击每个账号只失败一两次不会被锁 |

> ⚠️ **最后两条尤其要注意**：主动说出"我知道它不够好，且知道正确做法是什么"，
> 比假装完美更有说服力。**"未做压测"这一条绝不要含糊**——
> 把并发正确性说成性能数据，一旦被追问就会很难看。

### Q20：如果再多给你两天，你会做什么？

按价值排序回答（体现判断力，而不是罗列功能）：

1. **本地消息表 + 定时补偿**——把"通知必达"做成真的可靠，同时消掉上面那个窗口；
2. **`remaining_slots` 的对账任务**——定期校验 `remaining = total - 有效订单数`，
   把"数据是否仍然可信"变成可监控的；
3. **按 IP 的登录限流**（Redis 滑动窗口）——补上撞库那条口子；
4. 前端体验：错误码到用户提示的统一映射表。

> "注意我把'加功能'排在最后。**这个项目现在缺的不是功能，是可靠性细节。**"

## 十、这个项目里我踩过的坑（被问"遇到什么困难"时用）

**统一用"保护措施没接上"这个主题讲**——它比罗列 bug 更有洞察：

| # | 坑 | 教训 |
| --- | --- | --- |
| 1 | `@Transactional` 把登录失败计数一起回滚，**账号永远不会被锁定** | 业务异常默认触发回滚，而"失败计数"恰好在抛异常那条路径上 |
| 2 | 集成测试自己加了 `@Transactional`，**把上面的 bug 藏了整整一轮** | 测试级事务会掩盖真实事务边界的 bug |
| 3 | `ON DUPLICATE KEY UPDATE` 没有唯一索引可触发，**预置数据每次重启膨胀** | 写"防重复"之前先确认唯一约束真的存在 |
| 4 | JOIN 里两个表都有 `name` 列，**科室名显示成医生名且不报错** | 同名列 + 位置映射 = 静默串位 |
| 5 | 少一个 `@ExceptionHandler`，**缺参数返回 500** | 状态码要反映谁该负责；漏写处理器不会编译报错 |
| 6 | `push.ps1` 的 BOM 守卫不递归，`scripts/` 下的脚本完全不受保护 | **保护措施没覆盖到新位置 = 没有保护** |

> **总结句**（这句话是这份文档里最值得背的）：
>
> "这六个坑是同一个主题的重复：**保护措施没有真正接上**——
> 事务边界没接上、唯一索引没接上、列别名没接上、异常处理器没接上、
> 连那个防 BOM 的守卫自己也没接上。
> **每一次的代码都'看起来是对的'。**
> 所以我现在写完一道防线，会多问一句：**它覆盖的范围，和我以为的一样吗？**"
