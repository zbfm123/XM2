# 需求与范围

> **这份文件的作用是"防止范围蔓延"。**
> 3 天时间，写进来的每条需求都要能做完；写下"不做"的，是主动决策而非遗忘。

---

## 一、背景与定位

**场景**：患者在线上选择科室 → 医生 → 号源 → 提交挂号 → 收到通知 → 可取消。

**为什么选这个题**：

| 理由 | 说明 |
| --- | --- |
| 业务状态清晰 | 挂号有"待支付 → 已支付 → 已就诊 → 已完成/取消"，天然需要状态机 |
| **RabbitMQ 有真需求** | 挂号成功异步通知、**15 分钟未支付自动取消**（延迟队列）——不是硬塞的 |
| **天然需要并发控制** | 号源有限、多人在抢，**这是本项目的技术内核** |
| 面试官一看就懂 | 不需要你解释业务背景 |
| 与项目 1 完全不重合 | 业务、技术点都不重叠 |

---

## 二、角色

只有**一个角色**：患者（普通用户）。

> ⚠️ **管理员端本期不做**（见"不做清单"）。理由：管理端是最耗时的部分
> （每个实体都要增删改查 + 分页 + 表单校验），而它**体现不出任何技术深度**。
> 3 天里它是最该砍的。

## 三、功能需求

### F-01 用户（登录 / 注册）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-01-1 | 手机号 + 口令注册，口令 BCrypt 存储 | P0 |
| F-01-2 | 登录返回 JWT，后续请求带 `Authorization` | P0 |
| F-01-3 | 查询当前用户信息 | P1 |
| F-01-4 | 连续登录失败锁定（沿用项目 1 的做法） | P2 |

> **JWT 方案直接复用项目 1 的成熟做法**，不重新设计。
> 这是"复用已验证的东西"，不是偷懒。

### F-02 科室与医生（只读浏览）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-02-1 | 科室列表 | P0 |
| F-02-2 | 按科室查医生列表 | P0 |
| F-02-3 | 医生详情（简介、职称、所属科室） | P1 |
| F-02-4 | 医生排班列表（按日期、上下午） | P0 |

### F-03 号源与挂号（**核心**）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-03-1 | 排班包含：日期、时段（上午/下午）、**总号源**、**剩余号源**、挂号费 | P0 |
| F-03-2 | **提交挂号，扣减号源，防止超卖** | **P0（技术内核）** |
| F-03-3 | 同一患者对同一排班**不可重复挂号** | P0 |
| F-03-4 | 挂号接口**幂等**（重复提交返回同一订单） | P0 |
| F-03-5 | 号源为 0 时明确报错，不是静默失败 | P0 |
| F-03-6 | 我的挂号列表（分页、按状态筛选） | P0 |
| F-03-7 | 取消挂号，**归还号源** | P0 |
| F-03-8 | 已就诊/已完成的挂号不可取消 | P1 |

### F-04 异步通知与超时释放（**RabbitMQ 的落点**）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-04-1 | 挂号成功后**异步**发送通知（本期写库 + 日志，不发真实短信） | P0 |
| F-04-2 | **15 分钟未支付自动取消**（延迟队列），并**归还号源** | P0 |
| F-04-3 | 通知失败不影响挂号本身成功（**MQ 挂了不能拖垮主流程**） | P0 |

> ⚠️ **F-04-3 是重点**：很多人做 MQ 会把"发消息"和"主事务"绑在一起，
> 结果 MQ 一抖动，用户就挂不上号。**本项目明确要求解耦**，
> 并且这一点会写成测试。

### F-05 状态机

挂号的合法迁移：

```
PENDING_PAYMENT ──→ PAID ──→ COMPLETED
        │             │
        └─────────────┴──→ CANCELLED
```

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-05-1 | 合法迁移有**穷举单测**（沿用项目 1 的做法） | P0 |
| F-05-2 | 非法迁移抛异常且状态不变 | P0 |
| F-05-3 | 终态（`COMPLETED` / `CANCELLED`）不可再迁移 | P0 |

## 四、非功能需求

| 编号 | 需求 | 为什么重要 |
| --- | --- | --- |
| N-01 | **并发下不超卖** | 本项目技术内核，**有并发测试证明** |
| N-02 | 挂号接口幂等 | 用户双击 / 网络重试不能产生两个号 |
| N-03 | 错误分支有明确错误码 | 沿用项目 1 的纪律 |
| N-04 | 干净机器可复现（含部署脚本） | 面试时能现场起 |
| N-05 | 敏感信息不进仓库 | Git 历史上踩过这个坑 |
| N-06 | **MQ 不可用时主流程不受影响** | 与项目 1 的"降级"一脉相承 |

## 五、明确不做（主动砍，不是遗忘）

| 项 | 为什么不做 |
| --- | --- |
| **管理端**（科室/医生/排班的增删改查） | 最耗时、最无技术深度。**数据用 SQL 脚本预置** |
| **真实支付** | 涉及第三方，联调成本 > 收益。挂号直接进 `PAID` 或模拟回调 |
| **真实短信/邮件** | 需要账号与费用。改为**写通知表 + 打日志**，消费者逻辑完全一致 |
| 退号退费、评价、病历 | 与核心亮点无关 |
| 微服务拆分 | 3 天内拆了只会更差，且**没学过** |
| 分布式事务（Seata） | 本项目不需要，硬加就是炫技 |
| 号源动态放号、预约提醒 | 锦上添花，时间不够 |

> **"不做"清单比"做"清单更重要**——它决定了 3 天后你交付的是
> "一个完整的系统"还是"一堆半成品"。

### 最不能砍的三项

与项目 1 一样，明确列出**绝不砍**：

1. **A-03 并发不超卖**（技术内核）
2. **A-07 MQ 不可用不影响主流程**（与项目 1 的降级一脉相承）
3. **A-08 状态机穷举**（工程纪律的体现）

> 其余都可砍。**这三项砍了，项目就变成"又一个 CRUD"。**
