## Day 2：核心（最关键的一天）

### T-006 **号源扣减（防超卖）** ← 技术内核

| 项 | 内容 |
| --- | --- |
| 交付 | `ScheduleMapper.tryDeduct(scheduleId)`：一条原子 UPDATE |
| 验收 | **A-03**：**1000 线程抢 20 个号**，断言 ①订单恰好 20 条 ②`remaining_slots` 恰好 0 ③无负数 |
| 要点 | **禁止"先查再改"**；用受影响行数判断成败；失败不补偿 |

**这是全项目最重要的一条测试。** 写不出来就别往下走。

### T-007 提交挂号（幂等 + 唯一约束）

| 项 | 内容 |
| --- | --- |
| 交付 | `POST /api/appointments`，带 `idempotencyKey` |
| 验收 | **A-04**：同键重复提交返回**同一订单号**，且只建一条；不同键正常建新单 |
| 要点 | `idempotency_key` 唯一索引 + **`(dedup_key, schedule_id)` 唯一索引**（活跃订单唯一）双保险；号源为 0 时返回明确错误码 `NO_SLOTS_AVAILABLE` |

> ⚠️ **实施时的修正（T-007 已做，别再改回去）**：任务书写的是
> `(user_id, schedule_id)` 唯一索引，但那个语义是错的——它会让**已取消的订单**
> 继续占位，导致"取消后无法重新挂同一个号"。
> 正确语义是"同一排班同时只能有一个**活跃**订单"，实现上用生成列
> `dedup_key = IF(status='CANCELLED', NULL, user_id)` 表达。
> 详见 `02-architecture.md` 的"第二道防线"与 `PROGRESS.md` 的 T-007 踩坑记录。

### T-008 取消挂号（归还号源）

| 项 | 内容 |
| --- | --- |
| 交付 | `POST /api/appointments/{no}/cancel` |
| 验收 | **A-05**：取消后号源 +1，且**不超过总号源**；重复取消幂等；终态不可取消 |
| 要点 | 归还也用原子 SQL：`SET remaining = remaining + 1 WHERE remaining < total_slots` —— **加上界判断，防止取消把号源加超** |

> 这个细节容易被忽略：**如果只 `+1` 不判断上界，重复取消就会把号源加到超过总数。**

### T-009 我的挂号列表

### T-010 RabbitMQ 接入 + 异步通知

| 项 | 内容 |
| --- | --- |

| 验收 | 挂号后**异步**产生一条通知记录；消费者日志可见 |
| 要点 | **发送包 try/catch，失败只记日志**（决策 D-06） |

### T-011 **MQ 不可用不影响挂号** ← 绝不砍

| 项 | 内容 |
| --- | --- |
| 交付 | 测试：把 `MqPublisher` 换成总是抛异常的桩 |
| 验收 | **A-07**：**挂号依然成功**，订单状态正常，只是没有通知记录 |
| 要点 | 这与项目 1 的"AI 挂了规则不受影响"是**同一种纪律**，面试可以串起来讲 |

### T-012 延迟队列 + 超时自动取消

| 项 | 内容 |
| --- | --- |
| 交付 | TTL 队列 + 死信交换机 + 取消消费者 |
| 验收 | **A-06**：下单后 15 分钟（测试里改短，如 5 秒）订单自动取消、**号源归还** |
| 要点 | **只在订单仍是 `PENDING_PAYMENT` 时才取消**——已支付的不能被延迟消息取消掉（**这是个真实的坑**） |
